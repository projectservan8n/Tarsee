Names whose Rust shape is not the obvious translation:

  `fs_error_message(err, syscall, path)` and `fs_error_message_two` write an I/O error the way Node's `fs` did

- **url_safety**: `check_url_safety(url, Option<&dyn Settings>, &dyn Fetch) -> UrlSafety { safe, reason, level }`

## Differences from the Node behaviour

1. PNGs this module writes are deflated by flate2 (miniz_oxide), not zlib: the same pixels, different bytes. Icon
   versions come from the uploaded master's hash, so they do not change.
2. `fs` error texts are rebuilt from the I/O error kind (`ENOENT`, `EACCES`/`EPERM`, `EEXIST`, `EISDIR`, `ENOTDIR`,
   `ENOTEMPTY`, `EBUSY`, `EXDEV`, `EROFS`, `ENOSPC`, `ENAMETOOLONG`); any other error keeps Rust's text.
3. Download failures other than the guard's own refusal: "connect ECONNREFUSED host:port" names the host, not the
   IP Node showed; a failed name lookup is always "getaddrinfo ENOTFOUND host"; other errors give the innermost
   error's text. The guard's refusal and every message the JS made itself are identical.
4. `toLocaleString("en-US")` in pdf_read's "longer than N characters" note is written by hand (commas, up to three
   decimals); a fractional `max_chars` with a fourth decimal could round differently.
5. Text keeps UTF-16 units while a page is assembled (a character split over two font lookups still comes together),
   but a lone surrogate from a broken ToUnicode map ends up as U+FFFD; Node kept the lone surrogate. Cuts in UTF-16
   units (`fit_pages`, the downloaded file name, the original's name) drop a split pair instead of keeping half.
6. "no page {first}" for a page number of 1e21 or more prints its digits, not JavaScript's exponent form.
7. The files route parses JSON bodies itself as `express.json` did (application/json only, strict, empty is `{}`,
   50 MB then 413 "request entity too large"); a malformed body's 400 message is serde's, not V8's, and a
   non-UTF-8 charset parameter is not refused with 415.
8. pdftotext is found on the PATH of the app's environment (`which`), and started with that environment only; in
   production that is the process environment, so the result is the same.
9. On Windows the real path of a file (pdf_read's `locate`) is `canonicalize` with `\\?\` taken off: its letter case
   is the one on disk, where Node's `realpathSync` kept the case as typed. Only error messages show it.
10. `versionedManifest` threw on a `null` icon (a 500); the Rust treats any non-object icon as `{}`. brand.json's
    `version` and `updatedAt` are only read when they are strings. Neither happens with files Tarsee writes.
11. A PNG predictor whose row length is negative fails, as `Buffer.alloc` threw; the message imitates Node's
    RangeError text.

## Looks like a bug in the Node code (ported as it is)

1. **`POST /api/files/delete` can delete the whole workspace.** The guard is `ALLOWED_ROOTS.includes(resolved)`, a
   text comparison with `config.WORKSPACE_DIR`. When `TARSEE_WORKSPACE_DIR` is set with a trailing slash, a `..`, or
   (Windows) forward slashes, the resolved root never equals it, so `{ "path": "." }` removes the workspace.
2. **`POST /api/files/rename`** checks `newPath.startsWith(root)` without a separator (a sibling such as
   `workspace-old` passes), and `sanitizeFilename` keeps `/`, so a new name like `../x` moves the file to another
   folder; on Windows a `:` in the name makes an NTFS stream.
3. **`checkUrlSafety` is not a network guard**: 127.0.0.1, `localhost`, IPv6 literals and names resolving to private
   addresses pass. `pdf_read` has its own guard, but `web_fetch` in `lib/tools.js` relies on `checkUrlSafety` alone
   (S3 should know).
4. `pdfText`'s `own.error || pdftotextError`: `own.error` is always set on that branch, so pdftotext's error is
   never shown.
5. `saveBrandIcon` reads `prev.originalName` where a brand.json holding `null` makes `prev` null (a TypeError, 500).

## Risks

1. **`fetch_pdf` builds its own HTTP client** (reqwest, per download) instead of using `app.fetch()`. The Node code
   used `http.get` with its own `lookup` for one reason: the socket connects only to the addresses the guard checked,
   so no second DNS answer can point it at a private address. The client resolves names only through the given
   `Lookup` (`dns_resolver`), connects to exactly what it returned, uses no proxy (a proxy would resolve the name
   itself) and asks for no compression; redirects are followed by hand with the guard on every hop, IP literals are
   checked directly. A reviewer should check those builder calls first. Tests run it against a local server, as the
   Node tests did.
2. The hand-written PDF reader is large (about 1,500 lines of logic). The differential runs above give good
   confidence on browser-made PDFs and corruptions; PDFs from other producers (scanners, LaTeX, Word) were not
   compared.
3. Inflate on damaged data: zlib and miniz_oxide agree on every case tried, but how much partial output each gives
   at the point a stream breaks is the place they could differ.
4. The resizer copies the JS's `Float32Array` rounding; it is pixel-exact against the icons Node generated and
   committed (a test), and a change of one part in a million in an intermediate value breaks that test.
5. On Windows, `which` reads `PATHEXT` from the real process environment when it looks for pdftotext. (Fixed in
   round 1: see M6.)

### C2. A predictor asking for absurd sizes ended the process

`predict` no longer allocates a row on the file's word. When no whole row fits in the data actually present, it
returns nothing. Node's answer was the same: an empty buffer when its allocation succeeded, and a page reading ""
when it threw. A row length that is negative or endless is the RangeError it was.

I went through the whole reader for other places a number from the file sizes something:
- Stream `/Length` is compared as `f64` before any index is formed.
- An object stream's `/N` is capped at 1,000,000 and bounded by the numbers in its header; `/First` and the offsets
  are checked against the data.
- Differences codes index only 0 to 255.
- CMap ranges are bounded by their lists.
- Counts and depths are capped (pages 5,000, nesting 64, forms 6, references 32).
- Every other buffer is bounded by the bytes it decodes: ASCII85 and ASCIIHex, inflate at 64 MB a stream, and the
  256 MB budget.

The PNG decoder already checked width × height before allocating (the review confirmed this).

Tests:
- `pdf_text::a_predictor_asking_for_absurd_sizes_reads_as_an_empty_page`: `/Columns 1e12`, `1e20`, `2^64`, and
  `/Colors 1e6 /BitsPerComponent 1e6 /Columns 1e6` give `["", "second page"]`. Those are Node's answers, run on the
  same PDFs.
- `pdf_text::an_object_stream_with_an_absurd_predictor_does_not_end_the_process`.

### M2. JSON bodies Node accepted were refused

`json_body` now reads as `express.json` did:
- the charset is checked before the body is read: `utf-8` and the `utf-16` forms are decoded, and any other charset
  is 415 `unsupported charset "X"`;
- a leading byte order mark is dropped;
- a body of only a byte order mark is `{}`;
- a lone `\uD800`–`\uDFFF` escape is mended to U+FFFD before serde parses it. That is what writing it as UTF-8 gave in
  Node.

Test: `routes::files::json_bodies_are_read_as_express_json_read_them`.

### M3. `fs` error texts on Windows

`safe_path::uv_error` is now libuv's `uv_translate_sys_error` for every file-related Windows code, by raw OS code. For
example, `ERROR_INVALID_NAME` and `ERROR_DIRECTORY` give ENOENT, `ERROR_ACCESS_DENIED` gives EPERM, and
`ERROR_INVALID_FUNCTION` gives EISDIR. Unknown codes give `UNKNOWN: unknown error`. On Unix it uses errno where the
kind is ambiguous (EPERM or EACCES, ELOOP); the texts are from Node's `util.getSystemErrorMap()`.

Where Rust's own calls differ from libuv's, the route behaves as libuv did:
- writing to a folder gives EISDIR;
- a recursive mkdir gives EEXIST when a file is there and ENOTDIR when a file is on the way, as Node's mkdirp did;
- on Windows, a rename onto an existing folder gives EPERM. MoveFileExW refused it, while std's rename silently
  replaces an empty folder.

A NUL in a path gives Node's ERR_INVALID_ARG_VALUE text (`The argument 'path' | 'oldPath' | 'newPath' must be a
string, Uint8Array, or URL without null bytes. Received '...'`, quoted as `util.inspect` quotes) before any file
call. The cases the route can reach were run in Node on this machine first: writing to a folder, mkdir over or
under a file, a rename onto an empty or full folder, a NUL in each argument, an invalid name, rmdir on a file and a
300-character name. The rest of the table is libuv's, not run.

Tests: `routes::files::file_errors_are_nodes`, `safe_path::file_errors_read_like_node` and
`safe_path::a_nul_in_a_path_is_refused_with_nodes_words`.

### M4. pdftotext writing more than 64 MB ran to the time limit

### M6. Looking for pdftotext read the real environment

`which` is no longer used by this package. `find_program` is libuv's search:
- `PATH` comes from the app's `Env`, which matches `Path` on Windows.
- On Windows, the current folder is searched first, then each folder of `PATH`. In each, the name is tried as written
  when it has an extension, then with `.com` and `.exe`, so a `.cmd` or `.bat` is never run.
- On Unix, it takes an executable file in `PATH`, or in `/bin:/usr/bin` when `PATH` is not set (execvp's default).

Test: `it::pdf_text::pdftotext_is_looked_for_as_libuv_looked_for_it`.

### What `checkUrlSafety` checks, and what a guard for `web_fetch` needs

It is a reputation check, not a network guard. What it does:
- refuses `javascript:`, `data:`, `blob:`, `vbscript:` and any scheme other than http and https;
- passes the trusted domains (by the last two labels or the whole host) at once;
- warns on a raw dotted IPv4 host other than `127.0.0.1` (and now its IPv6-mapped forms); the URL parser writes
  decimal, octal and hex forms dotted, so those are caught;
- warns on the listed TLDs, the typosquatting patterns and a label over 30 characters;
- asks Google Safe Browsing when a key is set.

What it does not do:
- it never resolves a name, so `localhost`, `*.localtest.me`, `127.0.0.1.nip.io`, an internal DNS name or a name
  rebound to 169.254.169.254 all pass;
- `127.0.0.1` and IPv6 literals (`[::1]`, `[fd00::1]`, `[fe80::1]`) pass;
- it sees only the first URL: `web_fetch` follows redirects, so a public page that redirects to an internal address
  is fetched.

A guard for `web_fetch` would need what `fetch_pdf` does:
- refuse private IP-literal hosts (`is_private_address`) on every hop;
- resolve names only through a `GuardedLookup` that refuses a name with any private answer, and connect only to the
  addresses it returned (`dns_resolver(PinnedResolver)`), with no proxy;
- follow redirects by hand (`Policy::none`), checking each hop the same way;
- keep reading bodies with a size limit.

That cannot go through today's `Fetch` trait, which cannot pin an address. Either the tool builds this client as
`fetch_pdf` does, or `Fetch` gains a "guarded" request option. `checkUrlSafety` can stay in front as the reputation
check.

### Item 6: foundation helpers

My JavaScript white-space and trim helpers are gone in `pdf_text` and `brand_icon`; both use
`util::js::is_whitespace`, `trim` and `trim_end`. My old `normalize_path` and `join_path` are gone too, but not in
favour of `util::node_path::normalize`/`join`, because those are not Node's text:
- they keep a prefix as written (`//server/share`);
- they do not apply the CVE guard or the reserved names;
- `PathBuf::push` lets a name such as `b:s` replace the whole path. Checking a rename target that way would have
  been wrong.

The exact ports above replace them. `util::node_path::to_namespaced` is used as the design asks.

### Remaining differences, after this round

- An object stream whose predictor asks for a row the JS could not allocate: Node failed the whole PDF with the
  allocation error; the Rust reads that stream as empty. Content streams read the same in both (a page of "").
- A lone surrogate becomes U+FFFD as the body is parsed. That is the same in file contents. In a file name, and in
  the `path` echoed back, Node kept the lone surrogate (Windows) or wrote U+FFFD (Linux); the Rust always has U+FFFD.
- `utf-7` and `utf-32` bodies are refused with 415, where iconv-lite decoded them. A malformed body's 400 message is
  still serde's, not V8's.

## For package R4

The four cases of `test/brand-icon.test.js` ("brand icon: GET, POST and DELETE /api/settings/brand-icon") test
`routes/settings.js`. They belong in R4's `routes/settings.rs` tests, ported like this.

**Setup.**
- A test app.
- `BrandIcon::of(&app).reset_brand_icon()` first.
- The settings router with an `auditLog` stand-in that records each entry: whatever R4 uses for
  `req.app.get("auditLog")`, as an `{action, target, actor, ip, detail}` list.
- A signed-in session, as the Node test set `req.auth = { authenticated: true, method: "session" }`.

**The values the cases use.**
- `DEFAULT_VERSION = "d" + hex(sha256(public_dir/icon-512.png))[..11]`.
- `JPEG = [0xff, 0xd8, 0xff, 0xe0, 0, 16, 0x4a, 0x46, 0x49, 0x46, 0, 1]`.
- `SVG = <svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 10 10"><circle cx="5" cy="5" r="4"/></svg>`.
- `master_png(n)`: `encode_png(&disc(n, [30, 160, 90, 255], true))`, the full-bleed disc of `brand_icon/tests.rs`.
- `b64(bytes)`: standard base64.

**Case 1: `get_the_default_icon_s_state`.** `GET /api/settings/brand-icon` answers 200 with exactly
`{"custom": false, "version": DEFAULT_VERSION, "updatedAt": null}`.

**Case 2: `post_400_with_plain_words_for_what_is_wrong`.** POST each JSON body below. Each answers 400, and `error`
contains the given words:

| Body | `error` contains |
|---|---|
| `{}` | `master must be a PNG in base64` (the whole message: `The icon did not come through: master must be a PNG in base64.`) |
| `{"master": "%%% not base64 %%%"}` | `master must be a PNG in base64` |
| `{"master": b64(JPEG)}` | `must be a PNG` |
| `{"master": b64(encode_png(70x64, all [0,0,0,255]))}` | `square` |
| `{"master": b64(encode_png(flat 32x32 [0,0,0,255]))}` | `too small` |
| `{"master": b64(master_png(128)), "original": {"name": "a.png", "data": ""}}` | `original.data must be base64` (whole: `The original file did not come through: original.data must be base64.`) |
| `{"master": b64(master_png(128)), "original": "nope"}` | `original.data must be base64` |
| `{"master": b64(master_png(128)), "original": {"name": "a.txt", "data": b64("words")}}` | `not a PNG, JPEG, WebP or SVG` |

Afterwards `brand_status(&app).custom` is still false.

**Case 3: `post_a_good_one_is_saved_a_data_address_is_fine_too_and_it_goes_in_the_audit_log`.**
- Let `master = master_png(256)`. POST
  `{"master": "data:image/png;base64," + b64(master), "original": {"name": "icon.svg", "type": "image/svg+xml", "data": b64(SVG)}}`.
- It answers 200. Its body's `custom` is `true` and its `version` is `hex(sha256(master))[..12]`.
- A following GET answers the same body.
- `BrandIcon::of(&app).brand_dir()/original.svg` exists.
- The audit log has an entry with `action == "settings.brand_icon"`, `actor == "user"` and a `detail` that contains
  the version (the route writes `detail: "new icon <version>"`, `target: "brand-icon"`).

**Case 4: `delete_back_to_the_default`.**
- DELETE answers 200 with exactly `{"custom": false, "version": DEFAULT_VERSION, "updatedAt": null}`.
- The audit log has an entry with `action == "settings.brand_icon_reset"`.

**What the route does with this package's API.**
- `master` goes through `decode_base64_value`. Nothing means 400 with the first message above.
- `original`, when present and not null: its `data` (only if `original` is an object) goes through
  `decode_base64_value`. Nothing means 400 with the second message. `name` and `type` are taken only when they are
  strings, else `""`.
- The route calls `save_brand_icon(&app, BrandUpload { master, original })`. An error that downcasts to
  `BrandIconError` is a 400 with its text. Any other error is a 500
  `{"error": "The icon could not be saved: <message>"}` after `log::warn!("[brand-icon] save failed: ...")`.
- DELETE calls `reset_brand_icon(&app)`. An error is a 500 `{"error": "The icon could not be reset: <message>"}`.
