Names and shapes that are not the obvious translation:

- **`discord_format::js_text`** (new): JavaScript's `\s` as a class, its line terminators, and `translate(pattern)`,
  which turns a JavaScript pattern into a Rust one with the same meaning (`\s` with U+FEFF and without U+0085, `.`
  stopping at `\r`, U+2028 and U+2029, ASCII `\d \w \b`, `[\s\S]`, `\uXXXX`, a literal `[`, `~`, `&` inside a class).
  Every pattern of the package is written as the Node code wrote it and goes through it. The `i` flag (no `u`) is
  written as `(?i-u:...)` around the ASCII words it applies to. JavaScript's `trim` and whitespace are the
  foundation's `util::js::trim`/`trim_start`/`trim_end`/`is_whitespace` (since fix round 1).
- **discord_format:** `parse_md_tables` returns `Vec<MdTable>` (aligns as `Option<Align>`), `to_ascii_grid` returns
  `AsciiGrid { lines, width }`, `to_labeled_lines(headers, aligns, rows, bullet)` takes the `{ bullet }` option as an
  argument, `split_message_fence_safe(text, max_len)` takes the limit explicitly (2000 in the Node default).
- **reaction_parser:** `parse_reactions(&str) -> ParsedReactions { clean_text, reactions, buttons }`. A `Button`'s
  `text` and `data` are `serde_json::Value`, because the Node code passed the model's JSON values through as they were
  (`{"text": 7}` gives the number 7; Telegram's keyboard sends `text` as is).
- **slack_format:** `slack_text_to_plain(text, PlainOptions { bot_user_id, user_name })`; `split_for_slack(text,
  max_len)` (Node default `SLACK_MAX_MARKDOWN`); `MarkerFilter::{new, push, end}`.
- **slack_stream:** the client is the trait **`SlackClient`**: `start_stream`, `append_stream`, `stop_stream`,
  `post_message`, `update` (each `Value -> Result<Value, SlackApiError>`, Slack's own field names) and
  `set_agent_session_status`, whose default does nothing (the Node code called `agents?.sessions?.setStatus?.` only
  when the client had it). Errors are **`SlackApiError { code, message }`**: `SlackApiError::platform(code)` for
  Slack's `{ ok: false, error }` (message "An API error occurred: <code>", as @slack/web-api words it),
  `SlackApiError::other(message)` for anything else. `slack_error_code(&dyn Error)` gives the code of the first
  `SlackApiError` in the error's chain (the error, then each `source()`), so it also works on an `anyhow::Error`
  (`err.as_ref()`) with context added around it (since fix round 1; before, only the top level was read).
  `SlackReplyStreamOptions::new(client, channel, thread_ts)` fills
  the Node defaults; the stream is a cheap clonable handle with async `text`, `tool_start`, `tool_done`, `tick`,
  `finish` and the accessors `mode()` (`StreamMode::Native`/`Edit`, `as_str()` gives "native"/"edit"),
  `sent_text()`, `stopped_by_user()`. The queue is a `tokio::sync::Mutex` (FIFO); the flush timer is a tokio task.
  The Node `log` option is gone: warnings go through `log::warn!` with the same text.
- **email_parser:** `has_mention(stripped, keyword)` (pass `DEFAULT_MENTION_KEYWORD` for the Node default),
  `is_reply_all(ReplyAllCheck { stripped, subject, keyword, marker })` (`Default` gives the Node defaults),
  `thread_key_from_headers(&ThreadHeaders)`.
- **email_threading:** `build_reply_headers(incoming_message_id, references) -> ReplyHeaders { in_reply_to,
  references }`, `resolve_recipients(&IncomingMail, reply_all, self_address) -> Recipients { to, cc }`.
- **The mail structs package H3 fills** (exactly the fields these two files read):
  - `email_parser::ThreadHeaders { message_id: Option<String>, references: Vec<String> }`: the Message-ID and the
    References chain in header order, brackets kept.
  - `email_threading::IncomingMail { from, to, cc, reply_to }` of `MailAddress { address: Option<String> }`: `from`
    and `reply_to` are the first mailbox of From and Reply-To, `to` and `cc` every mailbox of To and Cc (what
    `channels/email.js` built from mailparser's `value` arrays). The body goes to `strip_quoted_reply` as the
    text/plain part, else `html_to_text(html)`.
- **tool_status:** `tool_status_label(name, &Value)`, `tool_done_label(name, &Value, is_error)`.
- **turn_notes:** the route event is read through the trait **`RouteLabels`** (`label()`, `provider_label()`),
  implemented for `serde_json::Value`; the turn layer's route type should implement it. `turn_error_note(route,
  message, TurnErrorOptions { clear_hint, plain })`, `idle_note(route, idle_ms: f64, plain)`,
  `stt_problem(code: Option<&str>, message)` (the STT error's code and message).
- **channel_errors:** `refused(message) -> RefusedError`; `is_refused(&anyhow::Error)` is the `err.refused` check
  (looks through context).
- **chat_target:** `resolve_chat_target(ResolveChatTarget { channel, channel_id, conversation_id, settings: Option<&dyn
  Settings>, db: Option<&Db> }) -> Option<ResolvedChatTarget { chat_id, thread_id, how: TargetHow }>`
  (`how.as_str()` gives "given", "this chat", "latest"); `conversation_of_chat(channel, &ChatTarget, Option<&dyn
  Settings>)`.

## Differences from the Node behaviour

1. **No half emoji.** Where the Node code cut text at a UTF-16 count with `slice`, a cut could split a surrogate
   pair: `turnErrorNote`'s 600-unit clip left half an emoji before the "…", and the Slack stream's
   `pending.slice(0, room)` (native) and `segText.slice(0, cut)` (editing) could end one message with half an emoji
   and start the next with the other half. Here the whole emoji goes to the next piece (or is left out of the clip).
   When the room left is one unit and the next character is an emoji, the emoji goes whole, one unit over, so the
   loop always ends. Cuts that do not land inside a character are unchanged.
2. **`split_message_fence_safe` ends when the room for a line is zero or less** (an open fence whose opening line is
   about as long as the limit). The Node code looped until it ran out of memory (`RangeError: Invalid array length`,
   reproduced); here such a line is cut one character at a time, and since fix round 1 the pieces are then cut to
   the limit (see "Node bugs fixed in the Rust version").
3. Inputs JavaScript accepted and Rust's types rule out (null, numbers where text was expected) are not accepted.
4. `toolStatusLabel("Read", null)` threw a `TypeError` in Node; `tool_status_label("Read", &Value::Null)` reads null
   as `{}` ("Reading file…").
5. A bot or user id that is not a valid pattern made `slackTextToPlain`/`mentionsUser` throw; here the mention is
   left in / nobody is mentioned. Valid ids are put into the pattern raw, as in Node (so `.` in an id matches any
   character, as it did).
6. `[buttons: ...]` JSON with a lone-surrogate escape (`"\ud800"`): `JSON.parse` accepted it, `serde_json` does not,
   so there are no buttons.
7. A panic in `on_stopped_by_user`/`on_native_unavailable` is caught, as Node caught a throw.
8. `slackEmojiName("constructor")` (or "toString", "__proto__"...) returned a function from `EMOJI_NAMES[s]`'s
   prototype in Node; here it is the name itself when it looks like a Slack name.

## Risks

1. **`js_text::translate`.** Every regular expression in the package passes through it. A reviewer should read it
   first, and the Node-comparison tables are what show it right; a pattern added later that uses JavaScript syntax it
   does not know (a lookahead) fails to compile at first use, in the tests.
2. **The Slack stream's queue and timer.** The tokio mutex hands itself out in request order, so calls run in the
   order they were made, as with the Node promise chain. The flush timer is a task numbered at arming; once it fires
   it removes itself and its flush is queued, which `finish` no longer cancels (as in Node). `tick()` from a timer
   task runs whenever it gets the queue.
3. The three lookahead patterns (`_italic_`, the quote marks, the bot-mention placeholder) and JavaScript's
   non-unicode case folding in `has_mention`/`is_reply_all` are matched by hand rather than with `fancy_regex` (whose
   `replace` panics on a backtracking limit). They are covered by the Node tables, but are the hand-written parts.
4. `slack_stream` relies on `serde_json`'s `preserve_order` for the field order of the Slack arguments; the scenario
   tests compare the serialized text, so a change there would show.

## Fix round 1

After the review (`E1-review.md`: faithful, two Minor findings) and two Node bugs the owner asked to fix rather than
carry over. 193 tests in the package now (182 before).

### Findings

1. **Turn notes trimmed with Rust's whitespace** (`turn_notes.rs`, three places). They use `util::js::trim` now, so
   a message with a byte order mark or U+0085 at an end is treated as Node treated it. Test:
   `messages_are_trimmed_as_javascript_trims_them` (the reviewer's six cases, expected values printed by Node). No
   other `str::trim` was left in the package.
2. **`slack_error_code` read only the top-level error.** It walks the error's chain now (the error, then each
   `source()`) and gives the code of the first `SlackApiError`, so H2 can add `.context(...)` without hiding
   `stopped_by_user` or `ratelimited`; the doc says so. Test: `the_code_is_found_under_added_context` (anyhow context
   once and twice, `Context` on a `Result`, an error type keeping the Slack error as its `#[source]`).

Also: the package's own JavaScript trim and whitespace helpers (`js_text::is_ws`, `trim`, `trim_start`, `trim_end`)
are gone; every module uses `util::js::trim`, `trim_start`, `trim_end` and `is_whitespace` from the foundation.
`js_text` keeps `translate`, the `\s` class text and `is_line_terminator`, which the foundation does not have. A new
test checks that the translated `\s` and `\S` agree with `util::js::is_whitespace` on every character.

### Node bugs fixed in the Rust version

1. **A hard cut made pieces over the limit when the line had emoji** (`discord-format.js:646`, also reached through
   `splitForSlack`). Node cut a too-long line into pieces of `budget` code points, so with emoji a piece was up to
   twice the limit: `"x".repeat(1999) + "😀".repeat(50)` at 2000 gave pieces of 2001 and 98 UTF-16 units, and
   Discord refuses a message over 2000. Now:
   - a hard cut counts UTF-16 units and falls between characters (that input gives 1999 and 100);
   - a last pass cuts any piece still over the limit. That happens only where the limit leaves no room for a
     reopened fence (a fence whose language tag is about as long as the limit, or a limit of a few characters,
     where Node ran out of memory); there the cut may go through a fence.

   No piece is longer than the limit, except a single character wider than the limit itself (an emoji with a limit of
   1). Tests: `no_lone_surrogates_on_a_hard_cut` (now pins [1999, 100]),
   `node_bugs_fixed_no_piece_is_over_the_limit_with_emoji_at_the_cut` (three inputs of the old Node table, which Node
   split into pieces of 42, 25 and 42 units at limits of 21, 20 and 25),
   `node_bugs_fixed_a_limit_too_small_for_a_fence_still_keeps_every_piece_within_it` (the reviewer's two inputs where
   Node ran out of memory), `slack_format::node_bugs_fixed_no_piece_is_over_the_limit_with_emoji`, and
   `no_piece_is_over_the_limit_and_fences_stay_balanced_on_generated_replies` (400 generated replies with emoji, flags,
   ZWJ families, CJK, long words, code blocks, CRLF or LF, at limits from 20 to 2000: no piece over the limit, every
   piece's fences balanced, no character lost).
2. **Fences in CRLF text were not recognised.** The Node fence patterns end in `(.*)$`, and `.` does not match "\r",
   so "```js\r" was not a fence line. Fixed in the three patterns that recognise fences; a fence line may now end in
   "\r", which is not part of its language tag:
   - `discord_format` (`FENCE_OF`): the splitter closes and reopens such a block (Node left its pieces unbalanced),
     and the table and quote formatters leave a table or quote inside it alone (Node redrew the table inside the
     block);
   - `slack_format::open_fence`, and so `close_fence` and the Slack reply stream: a block in CRLF text is closed at
     the end of a message and opened again in the next, in both streaming and editing (Node left it open).

   Tests: `node_bugs_fixed_crlf_fences_are_fences_when_splitting`, `node_bugs_fixed_a_table_inside_a_crlf_fence_is_left_alone`,
   `slack_format::node_bugs_fixed_a_crlf_fence_is_a_fence`,
   `slack_stream::node_bugs_fixed_a_crlf_code_block_is_closed_and_reopened_in_the_next_message`, and the generated
   replies above.

The Node-printed tables lost the entries that pinned the old behaviour: four from the split table and one each from
Slack's fence and split tables. Those inputs moved to the `node_bugs_fixed_*` tests with what the Rust version makes,
and the Node output is quoted in each test's comment. Every other entry is still compared with Node's own output. Each
fix was reverted once to see its tests fail.

### Note for H2 (from the review)

Node's Slack client (`@slack/web-api` 8.3.0, `rejectRateLimitedCalls = false`, `retryConfig =
tenRetriesInAboutThirtyMinutes`) waited out an HTTP 429 for its `Retry-After` and retried network errors before it
threw (`node_modules/@slack/web-api/dist/WebClient.js:431-451`). The reply stream switches a reply to editing
messages, for the rest of that reply, on **any** error but `stopped_by_user`. So H2's `SlackClient` must do the same
waiting and retrying before it returns an error (a rate limit or a passing network failure), or replies will fall back
to editing far more often than they did in Node.
