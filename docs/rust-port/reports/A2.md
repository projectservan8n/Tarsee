### The registry entry (A1)

`engine-env.js` does not import the registry: its functions take the entry. The Rust takes `impl Into<ProviderRef>`:
`ProviderRef::Id(&str)` (accepted for the plan only, else `TypeError`, as the JS) or `ProviderRef::Entry(&ProviderEntry)`.
`ProviderEntry` is a plain struct of exactly what engine-env reads; **A1's registry must provide a way to build one from
its entry** (e.g. `impl From<&Provider> for engine_env::ProviderEntry`, or `fn engine_entry(&self) -> ProviderEntry`):

| field | from `PROVIDERS[id]` |
|---|---|
| `id: String` | `id` |
| `label: Option<String>` | `label` |
| `engines: Option<Vec<String>>` | `engines` ("claude-code", "codex") |
| `env_key: Option<String>` | `envKey` |
| `base_url: BTreeMap<String, String>` | `baseUrl`, keyed by engine |
| `wrong_slot: Vec<WrongSlot { re: regex::Regex, message: String }>` | `wrongSlot` (`/^sk-ant-oat/i` is `(?i-u)^sk-ant-oat`: JavaScript's `/i` without `u` folds ASCII only, Rust's `(?i)` would also take `ſ` for `s` and the Kelvin sign for `k`; OPENAI_KEY needs `(?i-u:...|...)` so the flag covers both branches) |
| `models: Vec<EntryModel { id, context: Option<f64> }>` | `models[].id`, `models[].context` |
| `tiers: Tiers { fable, opus, sonnet, haiku: Option<String> }` | `tiers` |
| `default_model: Option<String>` | `defaultModel` (for claude/anthropic: `get_recommended_model()`) |

Until then the engine-env tests run on `registry()` in `src/ai/engine_env/tests.rs`, a copy of the registry's values
dumped from the Node module. At merge, replace `registry()`/`p()`/`PROVIDER_IDS` with A1's entries so the four
"agree with the registry" tests check the real table again.

## Differences from the Node behaviour

1. **Which codex runs** (design decision 3). Node: `codexBin`, else `TARSEE_CODEX_BIN`, else the binary of the pinned
   `@openai/codex` npm package for the platform. Rust: `codex_bin`, else `TARSEE_CODEX_PATH`, else `TARSEE_CODEX_BIN`
   (kept so an existing install that set it keeps working; drop it if the lead prefers), else `codex` found on the
   PATH (and PATHEXT on Windows) **of the `Env` given**, via `which` with a `Sys` that reads those two variables from
   it. The platform check ("Codex doesn't run on this system (plan9 x64).") is kept with Node's platform names. The
   missing message named the npm package; it now reads "Codex isn't installed here (no codex program on the PATH, and
   TARSEE_CODEX_PATH doesn't name one). Install Codex, or point TARSEE_CODEX_PATH at it."
2. `spawn_codex` on Unix puts the child in its own process group (`process_group(0)`); Node's `detached` also made it
   a session leader (setsid). `kill_tree` reaches the group either way.
3. `kill_tree` on Windows starts `taskkill` with the server's environment, as Node did (with an empty one it fails).
4. `run_codex` reports a signal by name on Unix ("SIGTERM"); on Windows there are none, as in Node.
5. A failed start is classified as Node's `spawn` classifies it (fix round 1): ENOENT, EACCES, EAGAIN, EMFILE and
   ENFILE are reported (`run_cmd`: code 127 with "Error: spawn sh ENOENT"); anything else is the error (`run_cmd`
   returns `Err(SpawnError)`, "spawn EPERM", where the JS promise rejected). On Windows an access-denied start is
   EPERM (libuv's name) and a folder is ENOENT (libuv looks for a file). A code the mapping doesn't know is written in
   Rust's words.
6. (Corrected in fix round 1.) The two guards that read JSON (the login-key check and the settings guard) read it as
   `JSON.parse` does (`engine_env/js_json.rs`): a lone surrogate escape, a number beyond f64 and any depth are read,
   and a later duplicate member wins. So they decide as Node did on every file. One deliberate difference, failing
   closed: on a file that isn't JSON at all, the login-key check also searches the text with its `\uXXXX` escapes
   written out, so a torn file can't hide a key behind an escaped name (`{"primaryApiKey": "sk-…", ` is refused;
   Node let that turn run).
7. (Corrected in fix round 1.) `home_for` takes the server's `Env`; the plan's home with no `home_dir` is
   `config::env::home_dir(env)`, never the process's own.
8. (The foundation now matches environment names in any case on Windows, as Node's `process.env` did.) Rust's
   `Command` merges environment names that differ only in case on Windows, which Node passed through twice; a child's
   environment map is still looked up in any case on Windows where the platform reads it (ComSpec).
9. `effective_context_window` returns `f64`; a route putting it in JSON must write a whole number without ".0".
10. `ensure_home` on Windows clears a read-only attribute (what Node's `chmod(0o700)` does there).

## Looks like a bug in the Node code (ported as it is)

- The CLI scan in test/claude-cli-env-names.test.js drops a name that ends exactly at the end of the file across a
  chunk edge (a match touching the end of a short last read counts as cut off unless it is in the last chunk).
- `os.tmpdir()` on Windows with no TEMP, TMP, SystemRoot or windir is "undefined\temp" (Node's own).
- `runCodex` waits for both streams to end: a program that leaves a grandchild holding stdout open after it exits
  waits until that grandchild exits, and the time limit can't stop it (its child is already gone).
- In `gatewayPins`, a tier override set to `undefined` replaces the entry's tier (spread) and becomes the main pin;
  Rust has no "set to undefined", so an absent override keeps the entry's tier.

## Risks (look here first)

1. `engine_env.rs`'s Codex config.toml reader (`read_key_path`, `codex_root_names`, `strip_codex_config`): byte-indexed
   where the JS indexed UTF-16 units, JS `\s` and `.` spelled out as explicit classes. All the JS cases pass; non-ASCII
   keys and odd whitespace are where a slip would hide.
2. The isolation and settings guards' file reading: invalid UTF-8 becomes U+FFFD (as Node's "utf8"), "missing" is
   NotFound or NotADirectory only; anything else refuses.
3. Linux: fix round 1 was built and tested in WSL (a copy of the worktree on the Linux file system, its own target
   folder): `cargo test --lib` 1154 passed, `cargo test --test it` 55 passed and 2 ignored, no clippy finding in this
   package's files. That run covers the Unix-only code, the round-1 additions included.
4. `codex_thread_dbs.rs` relies on SQLite behaving as better-sqlite3's did (both bundle SQLite with foreign keys on);
   the five-second busy wait in one test is real.
5. The registry copy in the engine-env tests must be swapped for A1's entries at merge.
