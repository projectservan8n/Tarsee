Names and shapes that are not the obvious translation:

- **`discord_admin(app, &args, DiscordAdminDeps { client, vault, log })`** is `discordAdmin(args, { client, vault,
  log })`. `client` is `&dyn DiscordClient` (below), `vault` an `Option<&dyn WebhookVault>` (`None`: the app's key
  vault, `AppVault(app)`), `log` an `Option<&dyn Fn(&str)>` (`None`: `log::info!`). `DiscordAdminDeps::new(&client)`
  is the production call. `resolveGuild(client, args)` is `resolve_guild(client, &args) -> Result<Guild, String>`
  (the error is the text the tool would answer). `permFlag(name)` takes `&str` and gives `Option<u64>`;
  `permLabel(bit)`, `maskWebhookUrl(id, token)`, `keyNameFrom(raw)` take `u64`/`&str`. `ACTIONS` is a `[&str; 5]`.
  Permissions are `u64` bit fields; `PERMISSION_FLAGS` is discord.js's `PermissionFlagsBits` (53 names, 52 bits, in
  its order), `perm::*` and `channel_type::*` name the ones used.
- **`railway_admin(app, &args, RailwayDeps { vault, env, log, timeout })`** is `railwayAdmin(args, { vault, env,
  fetch, log, timeoutMs })`. HTTP goes through `app.fetch()` (the JS `fetch` argument is the app's client). `vault`
  is `Option<&dyn RailwayVault>` (`get_key`, and `get_all_keys_decrypted` returning `None` for a vault that cannot
  list, the JS `typeof v.getAllKeysDecrypted !== "function"`); `env` an `Option<&Env>` (`None`: `app.env()`).
  `RailwayDeps::default()` is the production call. `DOCS` is a struct with the six documents (`DOCS.all()` is
  `Object.values(DOCS)`); `hereOf(env)` is `here_of(&Env) -> Here { project_id, environment_id, service_id }`;
  `maskValue` is `mask_value`.
- **The terminal.** `handleTerminalConnection(ws, req, { auditLog })` is two functions:
  `terminal_upgrade(app, WebSocketUpgrade, client_ip) -> Response` (sets the socket's limits, 100 MiB like `ws`'s
  default `maxPayload`, then runs the terminal) and `handle_terminal_connection(app, WebSocket, client_ip)`.
  `client_ip` is what the Node code read from `req` (`req.headers["x-forwarded-for"] || req.socket.remoteAddress`):
  `terminal_client_ip(&headers, Option<SocketAddr>)` gives it. The audit log is `app.get::<AuditLog>()` (Node passed
  the one `setupWebSocket` made). The module's `terminals` map is the `Terminals` service (`Terminals::of(app)`);
  `getActiveTerminalCount()` and `cleanupAllTerminals()` are `get_active_terminal_count(app)` and
  `cleanup_all_terminals(app)`. Added for tests and callers: `shell()`, `working_folder(app)`, `shell_env(app)`.

### What package H2 must implement: `discord_admin::DiscordClient`

The Node tool worked on the `discord.js` client; the trait is exactly what it asked of it. H2's Discord bot keeps a
connection that implements it, and its `Channel::admin(args)` is
`Ok(discord_admin(&app, &args, DiscordAdminDeps::new(&connection)).await)`.

| Method | discord.js call | What H2 does |
|---|---|---|
| `user()` | `client.user` | the bot's id; `avatar_url` = `displayAvatarURL({ extension: "png", size: 256 })`: `https://cdn.discordapp.com/avatars/<id>/<hash>.png?size=256` (`.gif` for an `a_` hash), with no avatar `https://cdn.discordapp.com/embed/avatars/<i>.png`, `i = (id >> 22) % 6` (discriminator "0") else `discriminator % 5`. `None` before login. |
| `is_ready()` | `client.isReady()` | logged in and ready. |
| `guilds()` | `client.guilds.cache` | the servers in the cache, in the order they arrived. |
| `fetch_guild(id)` | `cache.get(id) ?? fetch(id).catch(null)` | cache, else HTTP; any failure is `None`. |
| `fetch_channel(id)` | `client.channels.cache.get ?? fetch` | as above; a DM has `guild_id: None`. |
| `guild_channels(id)` | `guild.channels.cache` | every channel of the server held, active threads included. |
| `fetch_member(g, u)` | `guild.members.cache.get ?? fetch` | `display_name` = nickname, else global name, else username; `username`. |
| `create_channel(g, NewChannel)` | `guild.channels.create(...)` | `POST /guilds/{g}/channels` with `name`, `type`, `topic`, `parent_id`, and `permission_overwrites` as `[{id, type, allow: "<bits>", deny: "<bits>"}]` (left out when `None`), reason in `X-Audit-Log-Reason`. The Node test with the real client pinned this body. |
| `edit_channel(c, ChannelEdit)` | `channel.edit(...)` | `PATCH /channels/{c}`: `name`, `topic`, `parent_id` (`Some(None)` sends `null`), and with `lock_permissions` both `lock_permissions: true` and the category's overwrites (the new category's when `parent` names one, else the current one's), as discord.js sent them. Returns the channel as Discord sent it back. |
| `set_channel_position(c, pos, reason)` | `channel.setPosition(pos, { reason })` | discord.js took the channel's sortable group (`guild._sortedChannels`: same group of types, same category unless a category; sorted by position then id), moved the channel to index `pos`, renumbered the group from 0, and sent all of it in one `PATCH /guilds/{g}/channels`. The real-client test pinned `[{id: PROD, position: 0}, {id: NEW, position: 1}]`. |
| `edit_permission_overwrite(c, target, kind, set, reason)` | `permissionOverwrites.edit(target, set, { type, reason })` | `set` is the JS object in key order (true allow, false deny, null back to default). Apply it to the target's overwrite already on the channel with `apply_overwrite_set`, then `PUT /channels/{c}/permissions/{target}` with `type`, `allow`, `deny`. |
| `delete_permission_overwrite(c, target, reason)` | `permissionOverwrites.delete` | `DELETE /channels/{c}/permissions/{target}`. The only removal. |
| `fetch_webhooks(c)` | `channel.fetchWebhooks()` | `GET /channels/{c}/webhooks`: id, name, type, `user.username`. |
| `create_webhook(c, NewWebhook)` | `channel.createWebhook(...)` | `POST /channels/{c}/webhooks` with `name` and `avatar`: discord.js downloaded the URL and sent the image as a data URI; `None` sends `avatar: null`. Gives id and token. |

Every write's failure is a `DiscordError { code, message }`: Discord's JSON error code (50013, 50001, 10003, 30007,
50035, ...) and its message (`Missing Permissions`), as `DiscordAPIError` had them; `code: None` for anything that is
not an API error.

The structs carry what discord.js computed from its cache, and H2 must compute it the same way:

- `Guild.bot_permissions` = `guild.members.me.permissions`: `member_permissions(is_owner, &role_permissions)`
  (everything for the owner, else the union of the bot's roles, @everyone's included). `None` when the bot's member
  is not known.
- `Channel.bot_permissions` = `channel.permissionsFor(me)`: `member_channel_permissions(...)` (owner or
  Administrator: everything; else roles, then @everyone's overwrite, the roles' overwrites, the member's own). A
  thread takes its channel's. discord.js applied no implicit rule (no "cannot view, so nothing"): serenity's own
  `user_permissions_in` does, so use these functions instead.
- `Channel.everyone_permissions` = `channel.permissionsFor(guild.roles.everyone)`:
  `role_channel_permissions(guild_id, guild_id, everyone, everyone, &overwrites)`. `None` for a DM.

These four functions and `apply_overwrite_set` are discord.js's code, ported and tested here, so the arithmetic does
not depend on H2.

## Differences from the Node behaviour

1. **The Windows console asks for the cursor position (answered here; changed in fix round 1).** portable-pty creates
   the pseudo-console with `PSEUDOCONSOLE_INHERIT_CURSOR` (and two other flags) and has no way to leave it out;
   `node-pty` did not set it. The console's first output is therefore `ESC[6n`. The handler takes it out of the
   output, answers it itself (`ESC[1;1R`, top left) and sends the browser `ESC[2J ESC[H` in its place, which is how
   `node-pty`'s console began (it cleared the screen and started top left), so the page looks as it did. Unix is not
   affected.
2. **Starting the shell.** On Windows the shell is looked up in the `PATH` folders (whatever the case of the name),
   as `node-pty`'s `CreateProcessW` found it, and portable-pty is given the full path (fix round 1); on Unix
   portable-pty looks it up in `PATH`. A shell that is not there is `{"type":"error","message":"Failed to spawn
   shell: ..."}` and a 1011 close, as `node-pty` answered on Windows (its text: `File not found: `); on Unix
   `node-pty` started it anyway and the terminal showed `execvp(3) failed` and an exit with code 1. A working folder
   that does not exist: portable-pty starts the shell in the home folder (`HOME`, Windows `USERPROFILE`);
   `node-pty`'s shell failed (Unix: exit 1 after a `chdir` error; Windows: a spawn error). The configuration makes
   the workspace folder at boot, so this needs `CLAUDE_WORKSPACE_DIR` pointing somewhere missing. On Unix
   portable-pty also sets `SHELL` (from the environment, else the user's login shell) when the server's environment
   has none.
3. **Ending the shell (changed in fix round 1).** Unix: SIGHUP, as `node-pty` sent (bash passes it to its jobs);
   new: if the shell is still there 3 seconds later, SIGKILL to it and its process group (`node-pty` left a shell
   that ignores SIGHUP running). Windows: the shell is put in a job object when it starts, and the job is ended,
   which ends the shell and everything it started (whatever their ids) and nothing else, then the console is
   closed; `node-pty` ended the processes attached to the console (listed by a helper process). Differences: a
   program the shell started in a console of its own (`Start-Process -WindowStyle Hidden`) is ended here, where
   `node-pty` left it running (the dispatch asked for the shell's children to be ended); and when the session ends
   after the shell has exited by itself, what it left running is ended with the job (`node-pty` closed the console
   only). Without a job (the log says so), the shell alone is ended through its handle.
4. **The "node-pty unavailable" branch** (`{"type":"error","message":"Terminal unavailable: node-pty failed to load
   on this platform"}`, close 1011 "node-pty unavailable") has no counterpart: portable-pty is part of the program. A
   pseudo-terminal that cannot be opened goes the spawn-failure way.
5. **Smaller terminal points.** Output arrives in chunks cut where the reads fall (the joined text is the same).
   On Windows `node-pty` held writes and resizes until the console's first output; here they go at once (the
   console buffers them). A message whose JSON has an escaped lone surrogate cannot be read here (JS wrote U+FFFD
   to the shell). The logged reason for an unreadable message is serde_json's, not V8's. A message over 100 MiB:
   `ws` closed with 1009; here the same close is attempted after the library's own error (not tested: it needs a
   100 MiB frame).
6. **Railway, a request that fails to connect.** The reason in "Railway's API could not be reached (...)" was
   Node's error code (`ECONNRESET`, `ENOTFOUND`); here it is the HTTP client's message for the cause. A timeout reads
   the same ("no answer within 12 seconds").
7. **Railway, sorting names (changed in fix round 1).** `localeCompare` is ICU's collation. The Rust comparison has
   ICU's order for every ASCII character and every Latin letter from U+00C0 to U+02FF and U+1E00 to U+1EFF, read
   from Node: letters with their ASCII letter and their accents as marks with ICU's weights (in canonical order),
   letters ICU counts as two (`æ`, `œ`, `ß`, `ĳ`, `ǆ`, IPA digraphs such as `ʤ`), letters of their own (`þ`, `ŋ`,
   `ħ`, modifier letters) and five case classes (small, ligature, titlecase, capital, modifier). Checked against
   Node's sort of 17,781 random names: 3 pairs differ, all with an accent typed as a separate mark after a letter
   that has one already (ICU reorders the marks by combining class; the Rust does not). Other scripts are ordered
   by code point, which may differ from ICU.
8. **Railway, odd answers.** GraphQL `edges` that is not a list counts as empty (JS threw, giving "something went
   wrong: ..."); an answer with an escaped lone surrogate in it is "not an answer" here (JSON.parse took it). When
   two vault keys hold the value given as `value`, the key named is the first in the file (JS put keys that look
   like whole numbers first).
9. **Discord, a `type` named like an `Object.prototype` member** (`"constructor"`, `"__proto__"`): the JS lookup
   `TYPE_OF[typeKey]` found a function or an object, so the tool went on and sent Discord a broken request; here it is
   the "not one this tool makes" refusal.
10. **Discord, a vault that cannot be written:** the reason in "saving its URL to the vault failed (...)" is the
    Rust I/O error text, not Node's (`EACCES: permission denied, open ...`).

## Looks like a bug in the Node code

Ported as it is in every case.

1. **`edit_channel` with `sync_with_category: true` and `parent_id: "none"`** passes the check (`!edit.parent` is
   true for `null`) when the channel is in a category, and discord.js then gives the channel its old category's
   overwrites while taking it out of that category.
2. **The terminal's audit `ip` is the raw `X-Forwarded-For` header**, whole, while every other place uses Express's
   `req.ip` (one trusted hop). A client that connects directly can write anything there.
3. **`cleanupAllTerminals` is exported but nothing calls it.** At a graceful shutdown the shells were left to the
   operating system (they get SIGHUP when the server's end of the terminal closes on Unix). Z1 may want to call it.
4. **`list_channels` leaves out a channel whose category is not among the server's channels** (it is neither "not
   in a category" nor under a category).
5. **A custom vault whose `hasKey` throws** gets "Discord said: ..." (the error falls to the Discord error text). Not
   reachable with the real vault.

4. **The order of things when the shell and the socket end together**, and the waits: 200 ms (Unix) or 1 s of quiet

## Fix round 1

The review (`T1-review.md`) found 2 Critical, 1 Important and 4 Minor points, all in the web terminal and the
Railway sort. All seven are addressed, with two more points (the emoji cut in half, from the review's differential; the console's cursor
question, from the dispatch). Each fix was broken once afterwards (nine single changes in the terminal, plus the
Railway ones): each makes a test fail. Branch `port/T1-fix`, cut from `rust-rewrite` after the stopgap.

1. **Critical, a connection reset before `connected` left the shell running for ever.** A started shell is now held
   by a `Session` (in `terminal_handler.rs`), made in the blocking task that starts the shell, so it exists even if
   the socket's task is dropped while the shell starts. Its drop does what Node's `close` and `exit` handlers did:
   logs `[terminal] WebSocket closed for ...`, ends the shell if it is still counted (and so stops counting it),
   writes `terminal.disconnect`, and, when the shell has not ended yet, reports its exit (log line, `terminal.exit`)
   from a thread that waits for it. So a reset at any moment, a failed send (`connected`, output or the exit), the
   task dropped and a panic all end the shell and write the audit lines. Tests (`tests/it/terminal.rs`): a reset
   before `connected`, between `connected` and the first output, while output streams and during a large input
   (each: shell gone, count 0, audit `connect, disconnect, exit`), and the task dropped half way, both while it runs
   and while the shell is still starting. With the drop emptied the dropped-task test fails; without the handling of a
   failed `connected`, the test of a reset before it fails.
2. **Critical, ending the shell's process tree by parent ids on Windows.** The snapshot walk, the stopgap's
   `process_created_at` and `is_really_child`, and the `ToolHelp` feature are gone. The shell is put in a job object
   as soon as it is started (`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`); ending the session terminates the job (exit code
   1, as before) and closes it, so exactly the processes the shell started are ended, whatever their ids, and they
   also end if the server itself dies. If the shell cannot be put in a job, a warning says so (`[terminal] Could not
   put the shell in a job object (...): closing the terminal will end the shell alone`) and the shell alone is
   ended through the handle held. Tests: a process this test starts outside any terminal survives the terminal's
   close; a child attached to the console, a child in a hidden console of its own, and a grandchild in such a
   console (`cmd.exe` running `ping`) are all ended. With the job taken out, the test fails (the hidden ones
   survive).
3. **Important, an empty `PATHEXT` entry made portable-pty panic.** On Windows the shell is now looked up in the
   `PATH` folders (the name matched in any case) as `CreateProcessW` found it for `node-pty`, and portable-pty gets
   the full path, so it never reads `PATHEXT`; the shell's environment keeps `PATHEXT` exactly as the server has it.
   A panic inside portable-pty is caught and answered as a shell that could not start (`{"type":"error","message":
   "Failed to spawn shell: <the panic's message>"}`, close 1011), never as "task N panicked" (the panic message still
   goes to stderr through the default hook). Tests: a terminal with `PATHEXT=.COM;.EXE;.BAT;.CMD;` starts and runs a
   command; with no shell to be found and that `PATHEXT` (the panic path), the answer is the 1011 error with no
   "panicked" in it; unit tests for the lookup and the panic text.
4. **Minor, a close the browser starts was not answered.** On a close frame the handler flushes the socket, which
   sends tungstenite's queued answer (the same code and reason, as `ws` answered), then drops the socket, as `ws`
   ended the connection. Test: the client's `Close(1000, "bye")` gets `Close(1000, "bye")` back and the connection
   then ends cleanly; the shell is gone.
5. **Minor, a dropped connection logged an error.** A failed read is logged as `[terminal] WebSocket error for ...`
   only when `ws` would have emitted `error` (a broken frame, a message over the limit, text that is not UTF-8); an
   I/O error, a reset without a close frame and a closed connection only close, as with `ws`. Test (on a
   current-thread runtime so the handler's log lines are captured): a client that just goes away leaves
   `[terminal] WebSocket closed for ...` and no error line.
6. **Minor, Railway's sort of Latin letters outside Latin-1.** `locale_compare` moved to
   `src/lib/railway_admin/collation.rs` with tables generated from Node's own `localeCompare` (the generator was a
   throwaway script; the tables say how they were made): every Latin letter from U+00C0 to U+02FF and U+1E00 to
