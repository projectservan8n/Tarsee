Every exported name of the twelve Node files has its counterpart. The ones whose Rust name or shape is not the
obvious translation:

**`live_bus.rs`**
- `LiveBus::init(app)` / `LiveBus::of(app)` as DESIGN.md gives them, with the Node functions as methods. The Node
  names also exist as free functions taking `&App` (`publish(app, conv, type, payload, turn_id)`,
  `events_since(app, ...)`, ...). Like the Node functions before `initLiveBus`, they do nothing and answer with
  nothing when the app has no bus, so code and tests of later packages need not start one. The exception is
  `on_event(app, f)`, which panics without a bus: a listener that silently heard nothing would be a wiring mistake
  nobody sees.
- `publish`'s `{ turnId }` option is a plain `turn_id: Option<&str>` argument.
- **Listeners are registered callbacks**, not `broadcast` receivers. `on_event(f)` returns a `Subscription`;
  `subscription.off()` is the function the Node `onEvent` returned (dropping it does not unsubscribe, as ignoring
  the Node return value did not). A listener sees every event, in sequence order, and a slow one holds the others
  up: the `EventEmitter` semantics. A `broadcast` channel would drop events for a listener that falls behind.
  `subscribe()` gives the same stream as an unbounded channel for a listener that is an async task.
- `LiveEvent.r#type` keeps the Node field name (`type` is a Rust keyword). `ActiveTurn`, `RunningTool` and
  `QueuedTurnEntry` are the snapshot shapes; the fields a step may or may not have (`id`, `name`, `summary`,
  `lastStepLabel`) are `Option<Value>` so that absent stays absent and `null` stays `null`.
- `publish_message` takes a `TimelineMessage { id, role, content }` and the extra fields as a JSON map.
- New: `LiveBus::stop()` ends the hourly pruning (the Node interval ended with the process); `Drop` does too.

**`conversations.rs`**
- `ConversationStore::new(&app)` (cheap: make one wherever the Node code wrote `new ConversationStore(db)`). It
  finds the app's live bus when it needs it, so it works whether or not one was started. `for_db(db)` is a store
  over a bare database with no timeline.
- Rows are structs that serialise to exactly the Node objects: `Conversation` (`get`, `create`),
  `ConversationSummary` (`list`), `Message` (`get_messages`), `RecentMessage` (`get_recent_messages`: no token
  counts, as in Node), `AddedMessage`, `SearchResult`, `SessionRecap`. `to_json(&row)` gives the JSON object for
  code that builds a response out of rows (`{ ...conv, messages }`).
- Options objects are structs with `Default`: `NewConversation`, `ConversationUpdate`, `NewMessage`
  (`NewMessage::user("hi")`). Default arguments are constants: `LIST_LIMIT`, `RECENT_MESSAGES_LIMIT`,
  `SEARCH_LIMIT`, `RECAP_STALE_MINUTES`.
- **Writes return `rusqlite::Result`, reads do not.** `create`, `update`, `update_title`, `delete`, `add_message`,
  `delete_message`, `set_session_handle`, `clear_all_sessions` return the database's error (a message for a
  conversation that was just deleted is refused by the foreign key, as in Node, with the same text). `get`, `list`,
  `get_messages`, `get_recent_messages`, `message_count`, `search`, `get_session_handle`, `get_session_recap`
  answer with nothing and log when the database fails. This follows the sketch in `src/error.rs`
  (`store.get(&id).ok_or_else(...)`).
- `get_session_recap` is not async (the Node one awaited nothing).

**`conversation_lock.rs`**
- `with_conversation_turn(app, conv_id, opts, f)`: the closure is last (Node: `(convId, fn, opts)`). `f` returns a
  `Result<T, E>`, because the lock must know that a turn which waited failed before anything began (it ends the
  "Queued" line as failed). The result is `Result<Turn<T>, E>`; `Turn::QueueRemoved` is the Node `QUEUE_REMOVED`.
- It is **not an `async fn`**: the turn's place in the queue is taken (and `on_queued` called, and "turn_queued"
  published) when the function is called, as in Node, not when the future is first polled. The future must then
  be awaited or dropped.
- `claim_queued_turn`, `take_queued_note` and `current_queued_turn` take no app: they read the tokio task-local.
- New: `scope_queued_turn(queued, future)` carries the task-local into a task spawned from inside a turn (the Node
  `AsyncLocalStorage` followed spawned work by itself; a task-local does not).
- `reset_conversation_locks(app)` is `_resetConversationLocks`.
- The state is the service `ConversationLocks::of(app)`, made on first use.

**`chat_files.rs`, `sent_files.rs`**
- `ChatFiles::init(app)` returns `None` (and logs the Node line) when the table is missing. The Node functions are
  free functions taking `&App`; they keep nothing until `init` has run, as in Node.
- `place_files` and `place_files_on_page` take the messages as JSON objects (`&mut [Value]`: they add `files` and
  `filesAfter` to them) and return the lead files (Node: `{ messages, leadFiles }` / `{ leadFiles }`).
- `record_chat_files(app, conv, &[KeptFile], &RecordOptions)`; `KeptFile { name, size, path: PathBuf }`.
- The optional `{ dir = uploadsDir(), now = Date.now() }` arguments of `tidy_kept_files`, `keep_uploaded_files`,
  `keep_sent_file` and `viewable_path` are plain arguments: pass `uploads_dir(app.config())` and `now_ms()`.
- `note_sent_file(app, SentFile { .. })`, `note_received_files(app, ReceivedFiles { .. })`,
  `note_media_blocks(app, conv, blocks, MediaBlockOptions { .. })`.
- `send_viewable(&method, &request_headers, &file, &SendOptions)` is async and returns the `Response`. Express's
  `res.sendFile` (the `send` package) is written out by hand, checked against the real Express: see Risks.
- `view_kind`, `shown_name`, `disposition_name` take the path as text, as the Node ones did.

**`tool_steps.rs`, `message_tools.rs`, `handoff.rs`**
- Engine messages are read as `&serde_json::Value`. Steps are a `Step` enum that serialises to the Node objects
  (`kind` first); `step.to_value()` is the JSON for the timeline. `create_stream_watcher()` gives a
  `StreamWatcher`; `StreamWatcher::with_clock(f)` is the Node `{ now }` option.
- `slim_message(&Value) -> Value` (the message as a JSON object); `message_tools(&str) -> Vec<MessageTool>`.
- `build_handoff(&[Value], &HandoffOptions { max_chars, since })`; `since` is a JSON value (milliseconds or text),
  which is what the setting holds.

**`stream_utils.rs`**
- `init_sse()` returns `(SseStream, Response)`: the response to return from the handler, and what the Node code did
  with `res` afterwards: `send_sse(&sse, event, &data)`, `sse.end()`, `sse.writable_ended()`, `sse.destroyed()`,
  `sse.closed().await` (the "close" event). The route returns the `Response` and runs the turn in a spawned task
  that holds the `SseStream`.

**`gateway.rs`, `acp.rs`, `turn_watchdog.rs`**
- `GatewayManager::of(app)` / `get_gateway_manager(app)`, made on first use. A connection's `ws` is an
  `Arc<dyn GatewaySocket>` (`is_open()`, `send(text)`), which the WebSocket channel (Z1) implements.
  `connections()` is a snapshot of the Node `gw.connections` map.
- `ACPSession` and `ACPServer` are `AcpSession` and `AcpServer` (Rust's spelling of acronyms). The sessions belong
  to the app's `AcpServer::of(app)` (Node: one module-level map). A session's fields that change are read through
  methods (`turn_count()`, `messages()`, `status()`); `engine_session()` / `set_engine_session()` are the
  `session.engineSession` the Node route put on the object.
- `watch_turn(env, caller_left, WatchOptions)`: the Node function watched `res` for "close". An axum handler has
  no such event (its future is dropped), so the route gives a `CancellationToken` it cancels when the caller
  leaves before the answer is written (`token.drop_guard()` held in the handler, disarmed when it answers).
  `idled()`, `left()` and `signal()` are methods. Dropping the `TurnWatch` stops it.

## Differences from the Node behaviour

1. **Half an emoji is left out.** Wherever Node cut text with `slice` in the middle of an emoji it kept half a
   surrogate pair (shown as a broken character). Rust strings cannot hold one; the cut leaves the emoji out
   (`util::js`). Applies to every cap in this package.
2. **Stored JSON with half a pair.** Node wrote such a half as an escape (`"\ud83d"`) into timeline JSON and event
   payloads. `serde_json` refuses it, which would have made every old reply or event with one unreadable.
   `parse_json_lossy` (in `tool_steps.rs`) reads such JSON with the half left out. Used wherever this package
   parses stored JSON.
3. **Store reads do not throw** (see Files). A broken database gives "not found"/empty and a log line where Node
   gave a 500.
4. **The live bus after the database is closed** (shutdown) answers with nothing; Node's read functions threw.
5. **`on_event` needs the bus started first**, and a second `LiveBus::init` makes a new bus: listeners and turns in
   progress are not carried over (Node's emitter and maps were module-level and survived a second `initLiveBus`).
6. **An event published from inside a listener** reaches every listener after the event in hand (in sequence
   order). Node delivered it at once, so listeners registered later saw the inner event first.
7. **With several threads publishing**, `publish` can return a moment before its event has reached the listeners
   (another thread is delivering and takes it along). Order and completeness hold.
8. **Two turns arriving at the same instant on two threads**: their places in the queue are taken in call order,
   but their "turn_queued" events may be numbered the other way round. Node had one thread.
9. **A turn whose future is dropped or panics** (neither exists in Node): its slot is given back; its "Queued" line
   ends as `removed` when it had not begun, as `error` ("It could not start") when it had and no provider claimed
   it.
10. **Dates in free form.** `ms_of` and the handoff's times read SQLite's text and ISO times. Node's `Date.parse`
    also read free-form text ("Oct 27, 2026") and read an ISO time without a zone as local time; here it is UTC.
    Tarsee itself writes only the forms that read the same.
11. **JavaScript's coercions of wrong types** are not reproduced: a timeline `text` that is not a string is treated
    as empty, a tool id that is not a string is shown as text.
12. **Numbers.** A whole float is written as an integer where this package makes JSON text (`js_json`). A payload
    another package gives `publish` with a whole float goes out as `50.0`; the browser reads the same number.
13. **`send_viewable` on the wire.** axum writes `content-length: 0` on any answer with no body, the 304 included
    (Node sent none); hyper writes header names in lower case. Everything else was matched to Express.
14. **Gateway health snapshot** (nothing calls it, in Node or here): `uptime` counts from when the gateway was made
    (at boot), and `memory` is 0 on macOS (see below).
15. **Environment**: `TARSEE_EVENT_RETENTION_DAYS` and `TARSEE_CHANNEL_IDLE_ABORT_MS` are read as decimal numbers;
    JavaScript's `Number()` also took hex (`0x10`) and `Infinity`.

## Looks like a bug in the Node code

Ported as they are.

1. `conversation-lock.js`: a turn that starts another turn of its own conversation and awaits it waits for ever
   (the inner one queues behind the outer one). Nothing does this. A test pins the queueing.
2. `sent-files.js` `sendViewable`: the `sendFile` callback answers 404 for every error `send` reports, so a Range
   that cannot be satisfied (416) and a failed precondition (412) are 404s, with the headers set so far.
   (A suffix range longer than the file is "unsatisfiable" to `range-parser`, so that is a 404 too.)
3. `live-bus.js` `initLiveBus`: a `turn_start` with no turn id (within two days) gets a new `turn_end` at every
   restart, because `e.turn_id = s.turn_id` never matches NULL.
4. `conversations.js` `getSessionHandle`: forgetting an expired session also sets `updated_at` to now (the
   statement it reuses does), so an idle chat looks freshly active afterwards and its recap disappears.
5. `conversations.js` `addMessage`: a token count of 0 is stored as NULL (`||`).
6. `chat-files.js` `recordChatFiles`: when a row fails mid-way it returns `[]` although earlier rows were written.
7. `test/chat-files.test.js` "not on a reply that came hours later": the next message in its fixture is a user's,
   so the two-hour window is never reached. A Rust test now pins the window.
8. `gateway.js`: `getHealthSnapshot`, `checkFlood`, `getPresence` and `getConnectionCount` have no callers.

## Changes needed outside this package

1. **`util::js` additions.** This package needed JavaScript behaviour the foundation does not have yet. It lives
   as `pub(crate)` functions at the bottom of `src/lib/tool_steps.rs`, to be moved to `util::js` when convenient:
   `is_js_whitespace`, `js_trim`, `js_trim_start` (JavaScript's whitespace has U+FEFF and not U+0085, unlike Rust's),
   `collapse_whitespace` (`replace(/\s+/g, " ")`), `fold_blank_lines`, `js_string` (`String(value)`), `js_number`,
   `js_round` (`Math.round`), `js_json` (`JSON.stringify`, whole floats as integers), `serialize_js_number`,
   `parse_json_lossy`. Also `encode_uri_component` (`chat_files.rs`), `decode_base64_lenient` (`Buffer.from(x,
   "base64")`, `sent_files.rs`) and `real_path` (`fs.realpathSync`: `canonicalize` without the `\\?\` prefix on
   Windows, `sent_files.rs`); B2 will want the last one too.
2. **Process memory.** `process.memoryUsage().rss` has no standard-library counterpart. `gateway.rs` has
   `rss_bytes()` for Linux (`/proc/self/status`) and Windows (one FFI call to `K32GetProcessMemoryInfo`, the only
   `unsafe` in the package), and `None` on macOS. Five more Node files read it (`commands.js`, `self-heal.js`,
   `routes/admin.js`, `routes/analytics.js`, `routes/debug.js`): one helper in the foundation would serve them all.
3. **Routes that stream or outlive their caller (R1, and the external API and ACP routes).** In axum a handler's
   future is dropped when the caller disconnects. Node's "socket close never cancels a turn" therefore needs the
   turn to run in a spawned task: return `init_sse()`'s `Response` and give the `SseStream` to the task; for
   `watch_turn`, cancel a token from a drop guard in the handler. A turn spawned from inside
   `with_conversation_turn` must be wrapped in `scope_queued_turn(current_queued_turn(), ...)` or the provider
   cannot claim its "Queued" line.
4. **Z1** implements `GatewaySocket` for its WebSocket connections, and may call `LiveBus::stop()` at shutdown.

## Risks

What a reviewer should look at first:

1. **`conversation_lock.rs`.** The queue is hand-written (a holder ticket and a deque of waiters per conversation,
   one mutex over a few map operations, the slot held by a drop guard). The parts least like the Node code are the
   ways out that Node did not have: a dropped future, waiting or running, and a panic. Each has a test, and the
   suite ran 15 times in a row without a failure, but this is the module where a mistake costs most.
2. **`live_bus.rs` delivery.** Events are written and queued under the database's own lock (so sequence order is
   delivery order) and handed to listeners outside every lock by whichever thread is delivering. See differences
   6 and 7. A listener must not block for long: it holds up the timeline for everyone, as in Node.
3. **`send_viewable`** replaces a library with about 250 lines. Its answers were compared with Express for every
   case in its tests; what was not compared is behaviour under a connection that breaks mid-file.
4. **Store reads that swallow database errors** (difference 3): a choice, made to keep `store.get(&id)` an
   `Option`. If the lead prefers `Result` everywhere it is a mechanical change, best made before R1.
5. **Not run on Linux.** Everything was built and tested on Windows only. The Linux-only lines are the
   `/proc/self/status` read in `gateway.rs` and the `#[cfg(unix)]` symlink check in `sent_files/tests.rs`; path
   handling goes through `std::path` and was written for both.
6. `keep_uploaded_files`, `keep_sent_file`, `note_media_blocks` and `tidy_kept_files` use `std::fs` directly, as
   the Node code used the sync calls. A caller writing a large upload from an async handler may want
   `spawn_blocking` around them.
