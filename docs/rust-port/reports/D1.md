Every exported name of the twelve Node files has its counterpart. The ones whose Rust name or shape is not the
obvious translation:

**`live_bus.rs`**
- `LiveBus::init(app)` / `LiveBus::of(app)` as DESIGN.md gives them, with the Node functions as methods. The Node
  names also exist as free functions taking `&App` (`publish(app, conv, type, payload, turn_id)`,
  `events_since(app, ...)`, ...). Like the Node functions before `initLiveBus`, they do nothing and answer with
  nothing when the app has no bus, so code and tests of later packages need not start one. The exception is
  `on_event(app, f)`, which panics without a bus: a listener that silently heard nothing would be a wiring mistake
  nobody sees.
- `publish`'s `{ turnId }` option is a plain `turn_id: Option<&str>` argument.
- **Listeners are registered callbacks**, not `broadcast` receivers. `on_event(f)` returns a `Subscription`;
  `subscription.off()` is the function the Node `onEvent` returned (dropping it does not unsubscribe, as ignoring
  the Node return value did not). A listener sees every event, in sequence order, and a slow one holds the others
  up: the `EventEmitter` semantics. A `broadcast` channel would drop events for a listener that falls behind.
  `subscribe()` gives the same stream as an unbounded channel for a listener that is an async task.
- `LiveEvent.r#type` keeps the Node field name (`type` is a Rust keyword). `ActiveTurn`, `RunningTool` and
  `QueuedTurnEntry` are the snapshot shapes; the fields a step may or may not have (`id`, `name`, `summary`,
  `lastStepLabel`) are `Option<Value>` so that absent stays absent and `null` stays `null`.
- `publish_message` takes a `TimelineMessage { id, role, content }` and the extra fields as a JSON map.
- New: `LiveBus::stop()` ends the hourly pruning (the Node interval ended with the process); `Drop` does too.

**`conversations.rs`**
- `ConversationStore::new(&app)` (cheap: make one wherever the Node code wrote `new ConversationStore(db)`). It
  finds the app's live bus when it needs it, so it works whether or not one was started. `for_db(db)` is a store

  `SEARCH_LIMIT`, `RECAP_STALE_MINUTES`.

**`conversation_lock.rs`**
- `with_conversation_turn(app, conv_id, opts, f)`: the closure is last (Node: `(convId, fn, opts)`). `f` returns a

- `reset_conversation_locks(app)` is `_resetConversationLocks`.
- The state is the service `ConversationLocks::of(app)`, made on first use.

## Differences from the Node behaviour

(Fix round 1 narrowed 3, removed 12 and 15, and added 16 and 17: see "The differences from Node, as they now
stand" at the end.)

1. **Half an emoji is left out.** Wherever Node cut text with `slice` in the middle of an emoji it kept half a
   surrogate pair (shown as a broken character). Rust strings cannot hold one; the cut leaves the emoji out
   (`util::js`). Applies to every cap in this package.
2. **Stored JSON with half a pair.** Node wrote such a half as an escape (`"\ud83d"`) into timeline JSON and event
   payloads. `serde_json` refuses it, which would have made every old reply or event with one unreadable.
   `parse_json_lossy` (in `tool_steps.rs`) reads such JSON with the half left out. Used wherever this package
   parses stored JSON.
3. **Store reads do not throw** (see Files). A broken database gives "not found"/empty and a log line where Node
   gave a 500.
4. **The live bus after the database is closed** (shutdown) answers with nothing; Node's read functions threw.
5. **`on_event` needs the bus started first**, and a second `LiveBus::init` makes a new bus: listeners and turns in
   progress are not carried over (Node's emitter and maps were module-level and survived a second `initLiveBus`).
6. **An event published from inside a listener** reaches every listener after the event in hand (in sequence
   order). Node delivered it at once, so listeners registered later saw the inner event first.
7. **With several threads publishing**, `publish` can return a moment before its event has reached the listeners
   (another thread is delivering and takes it along). Order and completeness hold.
8. **Two turns arriving at the same instant on two threads**: their places in the queue are taken in call order,
   but their "turn_queued" events may be numbered the other way round. Node had one thread.
9. **A turn whose future is dropped or panics** (neither exists in Node): its slot is given back; its "Queued" line
   ends as `removed` when it had not begun, as `error` ("It could not start") when it had and no provider claimed
   it.
10. **Dates in free form.** `ms_of` and the handoff's times read SQLite's text and ISO times. Node's `Date.parse`
    also read free-form text ("Oct 27, 2026") and read an ISO time without a zone as local time; here it is UTC.
    Tarsee itself writes only the forms that read the same.
11. **JavaScript's coercions of wrong types** are not reproduced: a timeline `text` that is not a string is treated
    as empty, a tool id that is not a string is shown as text.
12. **Numbers.** A whole float is written as an integer where this package makes JSON text (`js_json`). A payload
    another package gives `publish` with a whole float goes out as `50.0`; the browser reads the same number.
13. **`send_viewable` on the wire.** axum writes `content-length: 0` on any answer with no body, the 304 included
    (Node sent none); hyper writes header names in lower case. Everything else was matched to Express.
14. **Gateway health snapshot** (nothing calls it, in Node or here): `uptime` counts from when the gateway was made
    (at boot), and `memory` is 0 on macOS (see below).
15. **Environment**: `TARSEE_EVENT_RETENTION_DAYS` and `TARSEE_CHANNEL_IDLE_ABORT_MS` are read as decimal numbers;
    JavaScript's `Number()` also took hex (`0x10`) and `Infinity`.

## Risks

What a reviewer should look at first:

1. **`conversation_lock.rs`.** The queue is hand-written (a holder ticket and a deque of waiters per conversation,
   one mutex over a few map operations, the slot held by a drop guard). The parts least like the Node code are the
   ways out that Node did not have: a dropped future, waiting or running, and a panic. Each has a test, and the
   suite ran 15 times in a row without a failure, but this is the module where a mistake costs most.
2. **`live_bus.rs` delivery.** Events are written and queued under the database's own lock (so sequence order is
   delivery order) and handed to listeners outside every lock by whichever thread is delivering. See differences
   6 and 7. A listener must not block for long: it holds up the timeline for everyone, as in Node.
3. **`send_viewable`** replaces a library with about 250 lines. Its answers were compared with Express for every
   case in its tests; what was not compared is behaviour under a connection that breaks mid-file.
4. **Store reads that swallow database errors** (difference 3): a choice, made to keep `store.get(&id)` an
   `Option`. If the lead prefers `Result` everywhere it is a mechanical change, best made before R1.
5. **Not run on Linux.** (Fix round 1 ran the package's unit tests on Linux.) Everything was built and tested on
   Windows only. The Linux-only lines are the
   `/proc/self/status` read in `gateway.rs` and the `#[cfg(unix)]` symlink check in `sent_files/tests.rs`; path
   handling goes through `std::path` and was written for both.
6. `keep_uploaded_files`, `keep_sent_file`, `note_media_blocks` and `tidy_kept_files` use `std::fs` directly, as

### I1. A Stop racing the slot — fixed

Two changes in `src/lib/conversation_lock.rs`.

1. **Removed and ended are one step.** `QueuedTurn::remove` sets `removed` and `ended` together under the flags
   lock, and only then tells the timeline. No thread can find the turn "removed, its line still open" any more, so
   nothing ends the line as "It could not start" in between.
2. **A removed turn comes back only once its Stop is done.** The first change alone left a second way to see
   something Node never showed. The Stop works on its own thread: it decides, then writes the `turn_end`, then calls
   `on_removed`. The turn could get its slot after the decision and return `Turn::QueueRemoved` before the other two
   had happened. Its caller then had "removed" in hand with no `on_removed` yet and no `turn_end` on the timeline,
   and the turn behind it could put its `turn_start` on the timeline in front of the removed line's `turn_end`.
   In Node the Stop had always finished by the time the slot came. Now a turn that finds itself removed waits for
   the Stop to finish (a `watch` flag the Stop sets when it leaves, however it leaves) before it returns and passes
   the slot on. The Stop waits for nothing of the turn's, so the two cannot wait for each other.

So in every order the two can land in, a queued message ends as one of the two endings Node has:

| | The Stop came first | The slot came first |
|---|---|---|
| `remove_queued_turn` | `true` | `false` |
| The turn | never runs, returns `QueueRemoved` | runs |
| Its line | `turn_queued`, `turn_end` "removed" | `turn_queued`, then the turn's own events |
| `on_removed` | called once, before the turn returns | not called |

**The stress test:** `a_stop_at_the_moment_the_turn_ahead_ends_is_either_in_time_or_too_late_never_a_failure`.

- Runtime with 8 worker threads, 20,000 rounds a run, each round a new conversation: a turn ahead, a queued turn
  with a line, and a Stop from another thread.
- The turn ahead and the thread that makes the Stop spin on one flag, so they set off together: one ends its turn
  (which hands the slot over), the other makes the Stop a few spins later. The number of spins follows the last
  round (a Stop that came in time holds the next one back, one that came too late lets the next one go sooner), so
  on any machine nearly every round lands within a few billionths of a second of the hand-over. The test fails if
  fewer than a tenth of the rounds land on either side.
- Each round checks the whole of the table above: what the Stop answered, what the turn returned, whether it ran,
  whether its caller had been told **at the moment the turn returned**, its line at that moment and afterwards, and
  that the queue is empty.
- What it showed:

| Code | Rounds that ended as Node never ends one |
|---|---|
| As reviewed | 8 to 22 of 40,000, in 6 runs of 6 (each one a removed line ended as "It could not start") |
| Change 1 only | 13,934 of 20,000 (the turn was back before its caller was told) |
| Both changes | 0 of 200,000 (10 runs on Windows), 0 of 40,000 (2 runs on Linux) |

- **The one break no test catches:** with change 2 in place, taking change 1 back alone (4 runs, 80,000 rounds,
  none wrong). The turn now waits for the Stop, so the Stop gets to write "removed" first. The wrong line is then
  only reachable when the turn's future is also dropped in that same instant, and there is nothing in the code to
  hold a test at that instant. Change 1 is kept because it is what makes the state true (a turn is never "removed"
  with its line open), so the drop guard never has to guess; and it is what turned the six failing runs of the
  stress test into passing ones, before change 2 existed.

**The other tests:**
- `a_removed_turn_comes_back_only_once_the_stop_that_removed_it_is_done`: a listener holds the Stop half way while
  the turn ahead ends. The removed turn has not returned and the turn behind it has not begun; when the Stop is let
  go the order is: the line ends, `on_removed`, then the turn returns and the next one begins.
- `a_stop_whose_on_removed_panics_still_lets_the_conversation_go_on`.

### M3. A turn begun right after the one before it finished is not told it queued — stands

- **Why.** In Node this came from the order of two promise callbacks: the queue forgot a finished turn one tick
  after the caller's own code went on. So `await turn(a); turn(b)` with nothing awaited in between called
  `onQueued(1)` for `b` and gave it a "Queued" line, though `b` waited for nothing. There is no such tick here: the
  slot is free the moment the turn's future completes. Copying the Node result would mean holding a finished turn's
  slot for a while longer on purpose, to show a person a "Queued" line for a message that is not waiting.
- The review found no caller that does this, in Node or here: every caller is its own message handler.
- It is now written down: in the module notes of `conversation_lock.rs`, as difference 16 below, and pinned by
  `a_turn_begun_right_after_the_one_before_it_finished_is_not_queued`.

### The rules that came after the package

**Joining paths** (`sent_files.rs`).
- The only names from outside that are joined to a folder are the names of kept copies. `kept_path(dir, front, name)`
  makes every one: the name is what `safe_file_name` made (the last piece of what was sent, with nothing but
  letters, digits and `_ . - space ( )`), it always has `chat-<time>-<n>-` or `sent-<time>-` in front of it, and
  should it ever hold a separator, a colon or a NUL it is "file". The join is `util::node_path::join`.
- `chat_files.rs` joins nothing: it stores and reads back the paths `sent_files.rs` made.
- Test: `an_upload_called_anything_at_all_is_kept_under_one_plain_name_in_the_folder`: `C:\Windows\win.ini`,
  `/etc/passwd`, `\\server\share\x.txt`, `..`, `a.`, `b `, `...`, `nul`, `nul.txt`, `con`, `a:b.txt` and an empty name.
  Each is kept under the name Node kept it under, exactly those files are in the folder, and nothing is written
  anywhere else. `a_kept_copys_path_is_in_the_folder_whatever_name_reaches_the_join` tests the join's own guard
  with names `safe_file_name` would never let through.

**File names on Windows** (`sent_files.rs`, `chat_files.rs`).
- Every file call on a path that holds a name from outside goes through `util::node_path::to_namespaced`, for the
  check and for the operation: reading the folder to tidy it, writing an upload, the `metadata`, `exists`,
  `hard_link` and `copy` of a sent file, each step of `real_path`, the `is_file` of `viewable_path`, the `metadata`
  and `open` of `send_viewable`, and the `gone` flag of a file's row in `chat_files.rs`.
- Tests, besides the one above: `a_sent_file_must_be_there_under_the_very_name_given` (`nul`, `...`, `secret.txt.`,
  `secret.txt `, `con` are no file; a file really called `report.` is kept as `report.`),
  `tidying_removes_the_copy_it_names_and_not_what_windows_would_make_of_the_name`,
  `a_copy_is_gone_unless_a_file_of_that_very_name_is_there`, and the M10 tests.

**Blocking file calls.** The functions with the JS names stay synchronous (S4 calls them, and their signatures are
unchanged). Each one that can take long has an `_async` twin that does the same work on the blocking pool, and

### What callers should know

Added, all new names:
- `ConversationStore::try_get`, `try_list`, `try_get_messages`, `try_get_recent_messages`, `try_message_count`,
  `try_get_session_handle`.
- `sent_files`: `tidy_kept_files_async`, `keep_uploaded_files_async`, `keep_sent_file_async`, `note_sent_file_async`,
  `note_media_blocks_async`.
- `tool_steps` (`pub(crate)`): `to_js_json`, `whole_numbers`, `js_number_from_str`.

What a caller sees differently:
1. **`on_removed` must not block.** A removed turn returns, and the turn behind it starts, only after `on_removed`
   has returned. (Send on a channel, end an SSE stream: yes. Wait for the turn: no.)
2. **`publish` returns `None`** when a listener panicked on that event (the event is written all the same), as the
   Node `publish` returned `null`.
3. **On Windows `viewable_path` gives the path as it was written** (when it is inside the folder), not the
   system's one true spelling of it. `keep_sent_file` likewise names the file as written.

For other packages:
- Any JSON text a route writes from a value that may hold a float (a stored payload, a timeline) should go through
  `to_js_json`, or Node's `1` is `1.0`. axum's `Json` does not.
- R1 keeps `viewable_path` in front of `send_viewable`, and uses the `_async` twins for an upload.

### The differences from Node, as they now stand

- **3** is narrower: a read that fails still answers with nothing, but a caller that needs to know has `try_`.
- **12** is gone: all JSON text this package writes has its numbers as JavaScript writes them.
- **15** is gone: both variables are read with JavaScript's `Number()`.
- **16 (new, M3).** A turn begun in the same tick as the end of the one before it is not told it queued and has no
  "Queued" line. Node told it "1 ahead".
- **17 (new).** A Stop runs on the thread that made it, so the turn it removed can get its slot while the Stop is
  still writing. The turn waits for the Stop; in Node there was nothing to wait for.
