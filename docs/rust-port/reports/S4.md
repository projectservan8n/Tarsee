Names and shapes that are not the obvious translation:

- **`createTarseeMcp(ctx, opts)`** is `create_tarsee_mcp(&App, ToolContext, CreateOptions { quiet }) -> TarseeMcp`.
  `TarseeMcp` is the server for one turn: `tools()` (`McpTool { name, description }` and `input_schema()`: what
  `lib/tool_registry.rs` needs), `list_tools()` (the `tools/list` result), `call_tool(app, name, arguments)` (the
  `tools/call` result, never fails), `begin(&Request) -> Step` and `handle_request(app, &Request)` (a whole JSON-RPC
  answer). The timezone in three texts is `app.config().timezone`.
- **The tools are written as the Node file wrote them**, with a stand-in for zod (`use schema as z`):
  `("channel_id", z::string().optional().describe("..."))`. The order of `.optional()` and `.describe()` matters and
  is kept: it decides where the description goes in the JSON Schema (probed, see below).
- **`startMcpHttp(opts)`** is `start_mcp_http(&App, StartOptions { state_dir }) -> anyhow::Result<EndpointInfo
  { host, port, url }>`; **`stopMcpHttp()`** is `stop_mcp_http(&App)`. The running server, the grants and the
  once-a-minute log memory are the app service `McpHttp` (`McpHttp::of(app)`).
- **`grantTurn(ctx, opts)`** (and `grantMcp`) is `grant_turn(&App, ToolContext, GrantOptions { turn_id, ttl, signal,
  leave_long_results }) -> anyhow::Result<Grant>`. It is always awaited (Node returned the grant at once when the
  endpoint was listening and a promise before). `Grant { url, token, expires_at }` has `revoke()`, and **dropping it
  revokes it**. See "For packages G1 and G2".
- **`grantCount()`** is `grant_count(&App)`; **`pruneToolOutput({ dir, maxAgeMs, now })`** is
  `prune_tool_output(&App, PruneOptions)`; **`spillThreshold(env)`** is `spill_threshold(&Env)`;
  `isLoopbackAddress`, `MCP_BODY_LIMIT`, `TOOL_OUTPUT_KEEP_MS`, `DEFAULT_GRANT_TTL_MS` keep their names. New:
  `MCP_TOKEN_ENV` ("TARSEE_MCP_TOKEN") and `claude_mcp_config(url)`.
- **`adaptMedia(content, caps, ctx)`** is `adapt_media(&App, &MessageContent, Option<MediaCaps>, &MediaContext) ->
  Adapted { text, media, content, saved, notes }`. `MediaCaps { vision, pdf }` is made `From` either kind of caps
  (`provider_registry::Caps`, `engine::TargetCaps`). The test seams of the Node `ctx` (`transcribe`, `pdfText`,
  `noteMediaBlocks`, `chatFilesFor`, `now`, `uploadsDir`) are fields of `MediaContext`; `settingsStore`/`store` is
  the one field `settings: Option<Arc<dyn Settings>>`.
- **`fileOfBlock`** (a `WeakMap` from a block object to the file it was saved to, so a retry or the backup model
  does not write a second copy) cannot exist here: blocks are values. It is `SavedBlocks`, which the turn makes once
  for its message and puts in `MediaContext::saved_blocks` for every `adapt_media` call of that message; a block is
  known again by its place in the message and its bytes. **G3 must do that**, or each attempt writes its own copy.
- **`writeLocalImages(media, { dir })`** is `write_local_images(&Env, &[ContentBlock], Option<&Path>) ->
  io::Result<LocalImages { inputs, dir }>` with `cleanup()`. The `Env` names the system's temp folder
  (`os.tmpdir()`, `lib::turn_leftovers::os_tmpdir`). Nothing is removed on drop: the turn calls `cleanup()`, as in
  Node.

### Proven against the real clients (by hand, on this machine)

Both programs were pointed first at the **Node** endpoint (to see what they send and what they make of its answers)
and then at the **Rust** endpoint, with a test token, a home of their own, no credentials, and their model hosts
set to a closed port. No model turn ran.

- **Codex 0.167.0** (`codex.exe app-server` with `mcp_servers.tarsee.url` and
  `bearer_token_env_var="TARSEE_MCP_TOKEN"`, the token in its environment): `mcpServerStatus/list` shows the server
  with all 27 tools (same names, and the description and schema it shows for `tarsee_send_message` are the ones
  sent); `mcpServer/tool/call tarsee_remember` reaches the tool with the granted context and its answer comes back;
  a call with a wrong type comes back `isError` with zod's words and runs nothing. It sends `initialize`
  (2025-06-18), `notifications/initialized`, `tools/list`, then `resources/list` and `resources/templates/list`
  (answered "Method not found", as by Node), each with `_meta.progressToken`.
- **Claude Code 2.1.319** (`claude.exe`): `claude mcp add-json tarsee '{"type":"http","url":...,"headers":
  {"Authorization":"Bearer ${TARSEE_MCP_TOKEN}"}}'` then `claude mcp list` prints `tarsee: http://127.0.0.1:<port>/mcp
  (HTTP) - ✔ Connected` with the token in the environment, and does not connect without the variable or with a
  wrong token. Started as an engine starts it (`-p --input-format stream-json --output-format stream-json --verbose
  --strict-mcp-config --mcp-config <config>`, the config once as JSON text and once as a file), its first message
  (`system`/`init`) lists `mcp_servers: [{name: "tarsee", status: "connected"}]` and all 27 tools as
  `mcp__tarsee__tarsee_*`. **So `${TARSEE_MCP_TOKEN}` in the headers is expanded from the program's environment**,
  in a stored server and in `--mcp-config` (text or file) alike.
  One thing worth knowing: Claude Code first asks `server/discover` with `Mcp-Protocol-Version: 2026-07-28`; the
  Node endpoint answers 400 ("Unsupported protocol version"), after which Claude Code sends `initialize`
  (2025-11-25), then `notifications/initialized`, a `GET /mcp` (405, which it accepts) and `tools/list`.
  The Rust endpoint answers each the same.

Both runs are repeatable: `TARSEE_TEST_CODEX=<codex> TARSEE_TEST_CLAUDE_CLI=<claude> cargo test --test it --
--ignored codexs_own_mcp_client claude_codes_own_mcp_client`.

## For packages G1 and G2 (and G3, which makes the grant)

One function gives a turn its tools, for either engine:

```rust
use tarsee::ai::mcp_http::{grant_turn, GrantOptions, Grant};

// Where ai/turn.js did `grant = await deps.grantMcp({ ...toolCtx, turnId, provider }, { turnId, signal })`:
let grant: Grant = grant_turn(
    app,
    ToolContext { turn_id: Some(turn_id.clone()), provider: Some(target.provider.clone()), ..opts.tool_ctx.clone() },
    GrantOptions {
        turn_id: Some(turn_id.clone()),          // names the folder long results go in
        signal: Some(stop.clone()),              // the turn's CancellationToken: cancelled, the grant is over
        leave_long_results: target.engine.as_deref() == Some(CLAUDE_CODE),   // see below
        ..Default::default()                     // ttl: 6 hours unless the turn has a timeout of its own
    },
)
.await
.map_err(|err| anyhow!("Tarsee's tools couldn't be opened for this turn: {err}"))?;
```

- It starts the endpoint if nothing has (Z1 also calls `start_mcp_http(&app, StartOptions::default())` at boot and
  `stop_mcp_http(&app)` at shutdown, logging `[mcp-http] could not start: <err>` as `server.js` did).
- **Hold the `Grant` for as long as the turn runs** (move it into the task or the stream that drives the engine).
  It ends when `revoke()` is called, when it is dropped (a turn that fails, is dropped, or panics), when the signal
  fires, or after its `ttl`. A request with an ended grant's token gets 401. A tool call already running when the
  grant ends runs to its end, as in Node.
- `grant.url` is `http://127.0.0.1:<port>/mcp`; `grant.token` is 32 random bytes in base64url (safe in an
  environment variable; never log it: `Grant`'s `Debug` leaves it out).

**Codex (G2).** `grant.mcp_grant()` is the `engine::McpGrant { url, token }` for `EngineOptions::mcp_grant`, and
`codex_options::McpGrant::from(&grant)` (or building it from the two strings) is what A5's `CodexContext::mcp`
takes. `build_codex_options` then writes `mcp_servers.tarsee.url = <url>`, `bearer_token_env_var =
"TARSEE_MCP_TOKEN"` (the constant `mcp_http::MCP_TOKEN_ENV`) and puts the token in Codex's environment under that
name, which is exactly what the endpoint expects: `the_options_codex_is_started_with_carry_the_grant_as_codex_reads_it`
builds the options from a live grant and gets in with them, and the real Codex was run with those settings.
A Codex engine called without a grant (its own tests) makes its own with `grant_turn` and keeps it until the turn
ends, as `codex.js` did.

**Claude Code (G1).** There is no in-process server any more: the program is given the same endpoint.

```rust
let config = grant.claude_mcp_config();       // or mcp_http::claude_mcp_config(&url)
// {"mcpServers":{"tarsee":{"type":"http","url":"http://127.0.0.1:<port>/mcp",
//                          "headers":{"Authorization":"Bearer ${TARSEE_MCP_TOKEN}"}}}}
let (name, token) = grant.token_env();         // ("TARSEE_MCP_TOKEN", <token>)
command.arg("--mcp-config").arg(config_file_or_json).env(name, token);
```

- The server's name is "tarsee", so the model sees `mcp__tarsee__tarsee_send_message` and so on, as before.
- The token is not in the config, so the config can go on the command line as text (no file to write or remove):
  Claude Code expands `${TARSEE_MCP_TOKEN}` from its own environment (run and seen with 2.1.319, as text and as a
  file). `engine_env`'s base environment strips `TARSEE_MCP_TOKEN` (it is in
  `AUTH_ENV_RE`), so G1 adds it to the child's environment itself. `grant.authorization()` is the literal header
  (`Bearer <token>`) if G1 prefers to write it into a private file instead.
- **`leave_long_results: true` keeps what Node did for Claude turns.** In Node only Codex's results were cut by
  Tarsee and saved under `tool-output/`; Claude Code got its tools in-process and cut long results itself
  (`MAX_MCP_OUTPUT_TOKENS`, `context_limits::mcp_output_env`). Without the flag the endpoint cuts first (same limit)
  and the model on Claude reads Tarsee's note instead of Claude Code's.
- Node logged `[mcp] Creating Tarsee MCP server: 27 tools, names: ...` at each Claude turn (and not for Codex). The
  endpoint builds its servers quietly, so to keep that line G1 calls
  `create_tarsee_mcp(app, ctx, CreateOptions::default())` once per turn (it is cheap) or drops the line.
- `EngineOptions::mcp_grant` and `engine::McpGrant` are documented as Codex's only (`ai/engine.rs`, I0): with
  decision 4 the turn layer passes a grant to both engines.

**Media (G2, G3).** `adapt_media(app, &content, Some(target.caps.into()), &MediaContext { conversation_id,
message_id, via, settings, label, saved_blocks: Some(turns_saved_blocks.clone()), ..Default::default() })` and use
`.content` (never fails; where Node's `adaptFor` caught a throw there is nothing to catch). The Codex engine writes
`write_local_images(app.env(), &pictures, Some(&codex_image_dir(app.env())))` and calls `cleanup()` when the turn
ends.

### A caller that goes away (design rule "A handler stops when the client leaves")

What `mcp-http.js` did when a request closed before its answer (`res.on("close")`): it closed that request's
transport, which made the SDK's server drop the answer of every handler still running for it; the tool itself
(`executeTool`, which takes no stop signal) ran to its end, its result went nowhere, no long-result file was written
for it, and that tool server was thrown away instead of being reused. The grant and everything else stayed as they
were.

Here, on purpose, the same: each `tools/call` runs in a task of its own and the handler waits for it on a channel.
When Codex or Claude Code hangs up (a tool timeout, a stopped turn), axum drops the handler; the task runs the tool
to its end and finds nobody to tell; nothing is saved for it. A grant that ends meanwhile changes nothing for a call
already running, as in Node. No lock is held across a wait, and nothing is half-updated when the handler stops (the
grant's counter of saved files moves only inside the task that writes the file). Tests:
`a_call_runs_to_its_end_when_the_caller_hangs_up_or_the_grant_ends_meanwhile` (it fails when the call is tied to the
handler: tried) and `a_request_dropped_half_way_leaves_the_endpoint_as_it_was` (a request cut in its request line,
its headers, at the blank line and in its body, and a body shorter than it says).

## Differences from the Node behaviour

1. **Both engines reach the tools over the endpoint** (design decision 4). What that changes for Claude turns is
   under "For packages G1 and G2": the token in the program's environment, long results, the "Creating" log line.
2. **On the wire, what a client cannot tell apart**: header names are in lower case (hyper), every answer has a
   `content-length` (Node sent the endpoint's own refusals and the 202 chunked), and the 202 has `content-length: 0`.
   Status, content type, `Cache-Control`, `Allow`, `WWW-Authenticate` and every body are the same.
3. **Bodies `JSON.parse` reads and `serde_json` does not.** Two are answered 400 "Parse error: the body is not
   JSON.": a number beyond a double (`1e999`: Node read Infinity, then refused it as a number or passed it on inside
   free-form arguments) and nesting past 128 levels (Node: served). Half of a surrogate pair written as an escape
   (`"\ud83d"`) is read with the half left out, as everywhere in the port (`lib::tool_steps::parse_json_lossy`),
   where Node kept the half.
4. **A long result cut in the middle of an emoji**: Node sent half of it; here the half is left out and the note
   says "The first 1,999 characters" (what is shown) where Node said 2,000.
5. **A whole number written with a decimal point** (`3.0`, `3e0`) reaches the tool as `3`. JavaScript could not
   tell them apart, and a Rust tool asking for a whole number would otherwise find none.
6. **Stopping the endpoint** lets a request in flight finish; Node destroyed every connection. In both, every grant
   is gone and the port is closed when `stop` returns.
7. **A batch that cancels one of its own requests** (`notifications/cancelled` beside the request it names): Node
   never answered that POST at all (run against the Node endpoint with a `ping` and with a tool call, the
   cancellation before or after: no answer, the connection just stays open). Here the notification has no effect
   and the request is answered.
8. **A batch with two requests under one id** gets one answer between them, as in Node; which one is the first to be
   ready, which is the same as Node's for the cases captured (an unknown method before a `ping`) but depends on
   timing when both run tools.
9. **`initialize` with malformed capabilities**: the capture's 48 `initialize` cases are answered the same, word
   for word. The SDK's `elicitation` shape has a preprocessing step that is not reproduced; it changes nothing a
   client can see.
10. **`grant_turn` refuses only a `ttl` of zero** (`Duration` cannot be negative or NaN), with Node's words.
11. **media, a compressed PDF's bytes**: none. (Recorded only because the test fixtures differ: the test PDFs are
    deflated by another library, so their sizes are checked against the file.)
12. **media, `SavedBlocks`** replaces the `WeakMap` (see Files): without it a retry writes a second copy.
13. **The log line** `[mcp-http] Tarsee's tools for Codex listening on 127.0.0.1:<port>` is kept word for word,
    though Claude Code uses the endpoint too now.
14. **A request whose caller leaves in the middle of its body**: Node logged `[mcp-http] a request failed: aborted`
    (once a minute at most). Here the handler is usually dropped before it can say anything; when it does get the
    error, the line ends with hyper's words for it instead of "aborted".
15. **A whole number past 2^53 in a tool's free-form arguments** keeps all its digits (JavaScript rounded it to the
    nearest double). A request id past 2^53 is refused, as by Node.

## Looks like a bug in the Node code (ported as it is, unless said)

1. `mcp-http.js` + SDK: a POST holding a request and a `notifications/cancelled` for it is never answered (not
   ported: difference 7).
2. SDK transport: two requests with one id in a batch get one answer, and the other handler's answer is thrown away
   after its tool has run (ported).
3. `mcp-http.js` answers 404 for a wrong path before it looks at the token, so a caller without a token can tell
   `/mcp` from other paths (ported; the caller is on this machine and the path is no secret).
4. SDK: an `initialize` whose parameters do not fit is treated as an ordinary request, so it is refused for a bad
   `Mcp-Protocol-Version` header where a well-formed one is not (ported).
5. `media.js` `keptCopies`: with the test seam `chatFilesFor` given and no message id, the files of every message
   of the conversation count, not only the latest one's (ported, seam included).
6. `media.js`: a document block that is not a PDF (and any block of a kind it does not know) is left out of the turn
   without a note, so the model never learns something was attached (ported).
7. `tarsee-mcp.js`: `tarsee_list_keys` and `tarsee_list_files` called with no `arguments` at all are refused
   ("expected object, received undefined") though they take none (ported; what the two programs send for a tool
   without arguments was not looked at).
8. `mcp-http.js` `spillThreshold`: a limit of `1000.6` rounds to 1001 while `999.9` is refused as under 1000 (ported).

## Risks (look here first)

1. **`src/ai/mcp_http.rs` `serve_request`**: the order of the refusals is the security of the endpoint (this
   machine only, Host, Origin, path, token, method, size). It is the Node order, each has a test that fails when the
   check is taken out, and the token is compared as Node compared it (SHA-256 of both, every live grant, constant
   time). The address of the caller comes from the listener (`LoopbackListener`), which a test can make lie
   (`report_callers_as`): that hook is `pub` only because tests need it.
2. **The Claude engine's token is in the program's environment**, so a shell the agent starts from Claude Code can
   read `TARSEE_MCP_TOKEN` (for Codex the shell's environment leaves it out). The token opens only this turn's own
   tools, on this machine, until the turn ends, under Tool Permissions: the same reach the agent already has. If G1
   wants it out of the shell's environment, the literal header in a private config file is the other way.
