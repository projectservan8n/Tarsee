Ported on branch `port/A5`. The three files of the package are done, with every case of their three Node test files
(66 of 66). The package has 103 tests (bridge 42, events 30, options 31).

Besides the ported tests, each file was compared with the Node code on the same inputs. A Node script (committed as
`docs/rust-port/reports/A5-capture-*.mjs.txt`) ran the Node functions and wrote their answers to a JSON file next to
the Rust tests; the `node_*` tests replay every input and compare:

Names and shapes that are not the obvious translation:

**`codex_events.rs`**

- The state is `CodexEventState`, made by `create_codex_event_state(CodexEventOptions { provider_id, model, baseline,
  baseline_known, local_url })` (`Default` has `baseline_known: true`). What `codex.js` read from the state is public:
  `thread_id`, `totals`, `done`, `tool_count`, `baseline_known`, `label`, `provider_id`, `last_error`, `last_retry`.
- Usage counts are `CodexUsage { input_tokens, cached_input_tokens, cache_write_input_tokens, output_tokens,
  reasoning_output_tokens }`, each an `f64` because they are JavaScript numbers (`Math.max(0, Number(x) || 0)`).
  `CodexUsage::from_value(&Value)` is the JS `normalizeUsage`; `usage_delta(&now, Option<&baseline>)` takes
  normalized usage (the JS normalized both itself; normalizing twice changes nothing). `to_value()` gives the JS
  object.
- `map_codex_event(&Value, &mut state) -> Vec<TurnEvent>`, `finish_codex_events(&mut state, FinishOptions { aborted,
  max_turns, error })` (`error` is the thrown error's message; an empty one reads as "Error", as
  `String(new Error(""))` did), `usage_events(&state, &totals)`, `unwrap_shell_command(&str)`,
  `classify_codex_failure(provider, message, FailureContext { model, local_url, status, code }) -> CodexFailure {
  kind: ErrorKind, recoverable, message }`, `RESULT_MAX_CHARS`.
- Each event is built as the JSON object the Node code yielded and read with `TurnEvent::from_value`; when the typed
  event would write different JSON (an item with no id gives a `tool_result` with no `id`; a numeric id stays a
  number) it is kept as `TurnEvent::Other` with the Node object. For Codex's real output every event is typed.
  `turn_types.rs` was not changed.

**`codex_options.rs`**

- `build_codex_options(&CodexTarget { provider_id, model, effort }, &CodexContext { ... }) -> Result<CodexOptions,
  EngineEnvError>`. `CodexContext` has every `ctx` field of the JS (`entry` is `Option<&'static Provider>`, `env` is
  an `Env` with no `process.env` default, `mcp` is `Option<McpGrant { url, token }>`, `local_bridge` is
  `Option<BridgeAddress { url, token }>`, `context_tokens`/`compact_window` are `f64`, `account_models` is the ChatGPT
  list as JSON rows, `platform` is Node's name for the system, default this one). A refusal is
  `EngineEnvError::Credential` (engine_env's codes and words), a caller's mistake `EngineEnvError::Type`, as the JS
  threw `CredentialError` and `TypeError`.
- `CodexOptions { provider_id, home, env: EnvMap, config: Value, api_key: Option<String>, thread_options }`;
  `ThreadOptions` has the JS keys (`model`, `modelReasoningEffort`, `sandboxMode`, `approvalPolicy`,
  `workingDirectory`, `skipGitRepoCheck`, `networkAccessEnabled`, `webSearchMode`, `additionalDirectories`) and
  serializes to the JS object; paths are `PathBuf`. `Debug` on these never shows a key or a token.
- `config` stays JSON (`serde_json` keeps insertion order), built in the JS order, so `config_args(&config)` (the JS
  `configArgs`, `Err(TypeError)` where it threw) gives Codex's `--config` arguments in the same order. G2 uses it to
  start Codex.
- `codex_effort(Option<&str>, allowed: Option<&Value>)`, `codex_model_for(provider, Option<&str>, Option<&[Value]>)`,
  `cap_instructions(&str, max_bytes)`, `instructions_limit(platform)`, `MCP_TOOL_TIMEOUT_SEC`.
- **New: `engine_entry(&Provider) -> engine_env::ProviderEntry`.** engine_env takes the entry it reads, and nothing
  built one from the registry yet (the follow-up "A1: build `engine_env::ProviderEntry` from the registry" in
  `STATUS.md`). It is here because this package is the first to need it; it belongs on `provider_registry::Provider`
  or in `engine_env` (G1 and G2 need it too).

**`local_bridge.rs`**

- `start_local_bridge(BridgeOptions { fetch, now, max_turn_ms, host }) -> io::Result<LocalBridge>`;
  `BridgeOptions::new(fetch)` gives the JS defaults. The JS `request` option is the `fetch` (an `Arc<dyn Fetch>`): the
  requests to the owner's server go through the `Fetch` trait, with no redirect followed and no timeout, the body
  streamed through without being gathered (except a reply that is not a stream and has calls to map back, which the
  JS gathered too).
- `LocalBridge { port(), open(upstream, key) -> Result<BridgeTurn, TypeError>, turns(), close().await }`. Dropping the
  `LocalBridge` stops the server. `BridgeTurn { url, id, token, release() }`; **dropping a `BridgeTurn` releases its
  turn** (the engine released it in `finally`; this makes it impossible to forget).
- The process's shared bridge (`localBridge()`, a module variable in Node) is an App service:
  `local_bridge(&app).await -> io::Result<Arc<LocalBridge>>`, started on first use (a start that fails is tried again by
  the next caller), its requests going through the app's HTTP client as it is at each request (`app.fetch()`), without
  keeping the app alive.
- The server is an axum `Router` (one fallback handler) served by `axum::serve` on `127.0.0.1:0`, through a listener
  of its own whose connections the server can cut: that is `res.destroy()` (a request whose turn closed while it
  waited, an answer that broke off) and `server.closeAllConnections()` in `close()`.
- Pure functions: `flat_name(&str, &str, Option<&HashSet<String>>)`, `flatten_tools(Option<&Value>) -> FlatTools {
  tools, names: ToolNames { by_flat, by_pair } }`, `rewrite_request(&Value) -> RewrittenRequest { body, names }`,
  `restore_item` / `restore_event(&Value, &ToolNames) -> Option<Value>` (`None` is the JS "the very same object":
  nothing changed), `create_sse_rewriter(names) -> SseRewriter { push, end }`, `redact_bridge_urls`,
  `CONTEXT_OVERFLOW_RE`, `MAX_TOOL_NAME`, `MAX_TURN_MS`. A namespace that had no name is `OriginalName.namespace:
  None` (the JS `undefined`).
- JSON the bridge re-writes is read with `serde_json` and written back with `js_stringify`, which writes numbers as
  `JSON.stringify` does after `JSON.parse` (`1.0` is `1`, a long integer is rounded as a double, `1e21` is `1e+21`):
  the server Codex talks to gets the bytes the Node bridge sent. `js_string`, `js_stringify`, `tpl` and `str_or_empty`
  are `pub(crate)` here and used by `codex_events.rs`; they belong in `util::js` with the other JavaScript helpers.

Every ported test passed on its first run, and so did every Node comparison but one: a capture input with an

was refused by the compiler. Of the 6 that got through:

- 3 were real gaps, now covered: a released turn must stop waiting for the owner's server (new test "releasing a

- 3 change nothing a caller can see: dropping the space after `data:` (the frame's JSON is the same with it),

## Differences from the Node behaviour

None on what Codex, the owner's server, the turn layer or the browser get from Codex's real output and real requests.
The ones below are on inputs that do not occur, or are invisible to a reader of the JSON:

1. **Bridge, idle connections:** Node closed a keep-alive connection that sat idle for 5 seconds
   (`server.keepAliveTimeout`). `axum::serve` has no such setting, so an idle connection stays open until Codex closes
   it (or the bridge closes). Codex's HTTP client reuses or drops its pooled connections itself; nothing waits on this.
2. **Bridge, header bytes:** Node read request headers as Latin-1 and wrote them back as Latin-1, so any byte passed
   through. Here a header value is text (the `Fetch` trait's headers are `String`s): UTF-8 passes through as it is, a
   byte that is not UTF-8 becomes U+FFFD. Codex sends ASCII headers.
3. **Bridge, why a server can't be reached:** the 502's words name refused, DNS, reset and timed-out connections as
   Node did, read from the Rust client's error; any other network failure is "network error" where Node showed its
   own error code ("EHOSTUNREACH").
4. **Bridge, JSON that `serde_json` refuses and `JSON.parse` takes** (a lone surrogate escape, a number past
   `1.8e308`, nesting deeper than 128): the body or frame goes through unchanged, where Node re-wrote it. And an
   object key that is a whole number ("0") keeps its place in a re-written body, where JavaScript moves such keys
   first. Neither occurs in Codex's requests or a Responses server's replies.
5. **Bridge, defaults of the HTTP client:** the request to the owner's server carries what `reqwest` adds by itself
   (`accept: */*` when Codex sent no `accept`) instead of what Node's `http.request` added.
6. **Bridge, a `BridgeTurn` dropped** releases its turn (above). Node's engine released it in `finally`, so the
   engine's behaviour is the same.
7. **Events, a cut through an emoji** (a tool result over 2,000 UTF-16 units, a thinking summary over 4,000, a status
   line over 240 or a retry reason over 120): Node kept half of the surrogate pair (written as `\udXXX` in JSON); the
   Rust cut leaves the emoji out (`util::js::utf16_truncate`, as DESIGN.md decided).
8. **Events, a patch whose `changes` holds `null`:** Node threw a `TypeError` (`c.kind` of null) out of the mapping;
   here it is a change with no kind and no path (an `Edit` of ""). Codex never sends one.
9. **Events, key order inside two typed events:** a `usage` event's counts are written in `turn_types.rs`' order
   (input, output, cache read, cache creation) and an `error` event's fields in `ErrorEvent`'s, not in the order the
   Node object listed them. Same keys and values; JSON readers see no difference.
10. **Options, `TARSEE_COMPACT_WINDOW`** is read from the `env` given only. Node's `compactWindowTokens(raw =
    process.env...)` fell back to the real environment when the given one lacked the name (a default parameter
    applies to `undefined`); callers pass the server's environment, so the value is the same.

## Looks like a bug in the Node code

Ported as it is in each case.

- `codex-options.js`: **`TARSEE_COMPACT_WINDOW=off` gives Codex `model_auto_compact_token_limit = 0`.**
  `compactWindowTokens("off")` is `null`, and `Math.min(null, n)` is `0` in JavaScript. "off" is meant to leave the
  window to the engine; Codex is told to compact at 0 tokens instead. Pinned by
  `compact_off_gives_a_compact_limit_of_zero_as_the_node_code_did` and the Node comparison. The fix would be to leave
  the key out when there is no window.
- `local-bridge.js`: a request whose body was still being read when its turn was released (or expired) still goes to
  the owner's server with the owner's key and is answered in full: its `AbortController` is added to the turn's set of
  live requests after `closeTurn` emptied it, so nothing ever aborts it. Only a request already authenticated before
  the release can do this.
- `local-bridge.js`: a GET or HEAD with a body is sent upstream with its `content-length` but without the body, so a
  strict server waits for bytes that never come. Codex never sends one.
- `codex-events.js`: `cleanCodexError` runs twice on a thrown error (in `finishCodexEvents` and again in
  `classifyCodexFailure`). Harmless: the second run finds nothing to remove.

## Changes needed outside this package

1. **`engine_entry`** (in `codex_options.rs`) should move to `provider_registry.rs` (`impl From<&Provider> for
   engine_env::ProviderEntry`) or `engine_env.rs`, closing the A1 follow-up; G1 and G2 need it.
2. **The JavaScript helpers** `js_string`, `js_stringify` (JSON.stringify of a parsed value), `tpl` and `str_or_empty`
   (`local_bridge.rs`, `pub(crate)`) belong in `util::js` with the others the cleanup collects.
3. **For G2:** the words for a missing `codex` program are still the Node ones ("the @openai/codex package or its
   program for this system is missing. Reinstall Tarsee's dependencies"), and `classify_codex_failure` gives them only
   for the SDK's and spawn's words ("Unable to locate Codex CLI binaries", "spawn ... codex ... ENOENT", "codex.exe:
   ENOENT"). The Rust engine finds `codex` on the PATH (ruling 10): if G2 reports a missing program in other words,
   it should either use one of those or the lead should reword this message for the Rust build.
4. **For G2:** hold the `BridgeTurn` for the whole turn (dropping it releases it); pass `local_bridge(&app).await`'s
   `open(upstream, owner_key)` as `CodexContext::local_bridge`; read a rollout's total into
   `CodexUsage::from_value`; start Codex with `config_args(&options.config)` as its `--config` arguments.

5. **Not this package:** `tests/it/voice.rs` `a_program_that_runs_too_long_is_stopped_in_node_s_words` failed once in a
   whole-suite run here (it asserts the run took under 4 s, and the machine was busy); it passed alone and in the
   next whole run.

## Risks

What a reviewer should look at first:

1. **The bridge's connection handling** (`BridgeListener` / `CuttableStream` / `Conn`, about 120 lines): cutting a
   connection from the server's side is hand-written over `axum::serve`. It is tested with the real client over
   loopback (Codex hanging up mid-stream, a turn released mid-answer, `close()` with a request waiting), on Windows
   only: this machine cannot build for Linux.
2. **`js_stringify` and `js_string`**: every body and frame the bridge re-writes goes through them; checked on the
   Node captures (floats, long integers, escapes, U+2028) but they are hand-written.
3. **The PowerShell wrapper pattern** in `unwrap_shell_command` is a `fancy_regex` (it needs a lookahead) with the
   `i` flag spelled out as ASCII letter classes.
4. **`TurnEvent::Other` for odd events** (`codex_events.rs` `event()`): only for Codex output that has never been
   seen (an item with no id, a non-text id, fractional or non-numeric usage). G3 must pass an `Other` on, as the
   I0 contract says.
