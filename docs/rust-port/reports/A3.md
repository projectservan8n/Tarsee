### The one conversion from the registry to the engine environment

Nothing in this package hands a registry provider to `engine_env`, so there is no `src/ai/engine_entry.rs`. A5 wrote
the conversion, `engine_entry(&Provider) -> engine_env::ProviderEntry`, in `providers/codex_options.rs`; as the lead
asked, it now stands beside `Provider` in `src/ai/provider_registry.rs` (with its test, in
`provider_registry/tests.rs`), and A5's code imports it from there. There is one such function in the tree.

The copy of the Node registry's values in `src/ai/engine_env/tests.rs` (A2's stand-in while A1 was being ported) is
gone: `registry()` there is now built from the real table through `engine_entry`, so the matrix-coverage test and
the three "agree with the registry" tests check A1's registry itself. All of A2's engine-env tests pass on it
unchanged, which also says the copy and the port held the same values. This closes STATUS.md's follow-up "A1: build
`engine_env::ProviderEntry` from the registry; replace the copied values".

### What runs when nobody waits

Work the Node code started and left running runs in a task of its own, so it finishes (or is cancelled on purpose)
whoever is waiting: the device sign-in from its start (`start_device_login` returns once the code is shown; a watcher
task follows the codex until it ends, times out or is cancelled), `login_status` when it asks the CLI, `logout`'s
sign-out, the account-models request (one in flight per home, shared by its callers) and `sync_chatgpt_catalog`.
Each has a test that drops the caller and checks the work still ended as it should, with no codex left running. A
codex is only ever stopped through A2's `kill_tree`.

## Differences from the Node behaviour

1. **Which codex runs** is A2's rule (design decision 3): `codex_bin`, `TARSEE_CODEX_PATH`, `TARSEE_CODEX_BIN`, then
   `codex` on the PATH of the `Env` given. The real-codex tests take the program's path at build time.
2. `login_status`: a `last_refresh` that is not an ISO date (V8 also reads "Nov 9 2026" and the like) is not read:
   the field is then absent, as for text V8 could not read either. Codex writes ISO dates.
3. `fix_settings_file` on a file that is not JSON says "it isn't valid JSON" where the JS message carried V8's own
   parse error text; a document nested deeper than 1,700 levels is refused on writing back ("Maximum call stack size
   exceeded", V8's words, at a depth of its own that depends on the stack).
4. `codex-models`: the app-server's lines are read with serde_json, not the JS-faithful reader: nothing is decided
   on them but the list they carry. A line that is valid JSON only to one of the two (a lone surrogate escape, a
   number beyond f64) is skipped here and was read there.
5. Text cut to a length (the sign-in's kept output, the models' error text) drops a half surrogate left at the cut;
   the JS kept it.
6. Provider status: a key's Railway variable is read from the App's `Env` whatever `deps.env` is (the Node store
   read `process.env` itself); a store is always asked for its key (the JS asked only a store that had
   `getKeyWithSource`); `saved_key_providers` counts a stored row or a value in the store given; a state folder
   that is only whitespace gives no key homes (the JS threw); `codex_home_for` cannot fail; `clear_failure_flag`
   has no options (the JS handed its third argument on to `store.delete`; `Settings::delete` takes none).
7. Spend, by type: `max_budget_usd` and `cost_usd` are numbers (the JS also read a ceiling from text) and a moment
   is milliseconds; `caps: Some(Caps)` is the caller's word on who keeps the ceiling (the JS fell back to the
   registry when the object had no `nativeBudget`); `monthly_cap_status` needs the database named (above).
8. Spend: when a row cannot be filed the log line carries SQLite's own message ("no such table: usage_turns", "The
   database connection is not open"), which is what `better-sqlite3` said for those two; another failure is in
   rusqlite's words.

## Looks like a bug in the Node code

Ported as they are:

- `spend.js` `spendBetween(db, from, to, { provider })`: a `provider` that is no provider narrows nothing, so the
  whole spend comes back rather than none. `monthlySpend` passes it through.
- `spend.js` `money`: a negative amount is "$-1.00", and one that rounds to nothing "$-0.00". No caller has a
  negative amount.
- `spend.js` `recordReportedCost`: an `endedAt` above 0 and under half a millisecond is stored as 0 rather than
  taken as missing.
- `spend.js` `tokensOf`: `true` counts as one token (`Number(true)`).

## Risks

1. **The device sign-in's two phases** (`codex_device_login.rs` `begin` and `watch_login`): the select loop that
   reads the prompt, the watcher task, and every way out of them (code shown, timeout, cancel, the codex ending
   early, a second start for the same home). Each has a test against the stand-in, and three against the real
   codex, but this is the code with the most interleavings. On Windows the stand-in is started through a `.cmd`
   shim so that `kill_tree` has a tree to end.
2. **Rewriting an owner's settings file** (`settings_guard.rs` `strip_claude_settings` + `js_json::stringify_pretty`):
   held to `JSON.stringify` by tests on order, escapes, numbers and nesting; a reviewer should try a file of their
   own.
3. **Which environment** provider status reads: `deps.env` for the turn's variables, the App's for a key's Railway
   variable (difference 6). The 380-scenario comparison covers both.
4. `iso_ms`/`iso_string` (V8's date rules for `last_refresh`) are written by hand; compared with Node on a generated
   list, not proven.
5. Everything that takes the owner's timezone depends on the foundation's zone parsing (above).
