# I0: Shared interfaces for the turn, tools, commands and channels

No behaviour of the turn layer, the engines, the tools, the commands or the channels was ported. This package is the
types and traits the other packages call each other through, a fake for each, and the guide to them
(`docs/rust-port/INTERFACES.md`, which the implementing agents should read first).

Names and shapes that are not the obvious translation:

- **`chat_stream(app, options)`** calls a `TurnRunner` stored in the app. In Node `chatStream` was `runTurn` itself,
  and channels took a `chatStream` option for tests; both are replaced by the installed runner.
- **`TurnStream` items are `anyhow::Result<TurnEvent>`.** `Err` is the Node generator throwing: the fake engine's
  `throw`, and what `background-turn.js`, `websocket.js`, `routes/acp.js` and `routes/chat.js` caught around their
  loops.
- **`EngineRegistry` has two layers**: `install(name, engine)` for an engine's own module (what `ENGINE_LOADERS`
  imported lazily; there is no lazy import in Rust), `register_engine(name, Some/None)` for the Node `registerEngine`.
- **`SessionChoice`** is the engine option `sessionId`, whose presence mattered (`Object.hasOwn(opts, "sessionId")`):
  `Unset`, `Fresh` (`null`), `Resume(raw)`.
- **`EngineMedia`** is the engine option `media`: an array from the turn layer, or `adaptMedia`'s `{media, text}`
  (one Claude engine test passes that form).
- **One name where Node had two for the same value**: `on_session_handle` (`onSessionHandle` and `onSessionId`),
  `mcp_grant` (`mcpGrant` and `mcp`), `TurnOptions::session_id` (`sessionId` and `sessionHandle`).
- **`ToolContext`, `CommandContext` and `TurnOptions` have no `db`, `settingsStore`, `auditLog` or `convStore`**:
  every caller passed them, so they are the app's. `ToolContext` has no `channelManager` either (a tool fell back to
  the app's). `CommandContext` keeps it, as `channel_manager`: one of its seven callers passed it and two commands
  answer differently for it (corrected in fix round 1; this line used to say it was the app's).
- **`Usage`'s counts are `Option<u64>`** (left out when the object had none), read with `input()`, `output()`,
  `cache_read()`, `cache_creation()` for the Node `|| 0`; `Usage::merge` is `{ ...usage, ...event.usage }`.
- **`ChannelApi::channel(kind)`** is the Node `manager.channels.get(kind)`; `kind` is the Node `type`.
- **A bot's missing method** (`!bot?.sendFile`) is a default method that fails with `Unsupported`.
- **`processCommand`** kept its name as `process_command` (the dispatch message calls it `handleCommand`; there is no
  such export).
- **`extract_playbook_prompt` is implemented here**, not only declared: it reads a result and nothing else, and the
  channels need it before K1 exists. `lib/commands.rs` should re-export it.

## Differences from the Node behaviour

None in behaviour (none was ported). In the shapes:

1. **Key order of `error` and `usage` events.** Each place in the Node code that builds one lists its keys in its
   own order (at least six orders for errors, two for usages). The Rust structs write one order (`message, subtype,
   recoverable, code, status, state`; `input, output, cache_read, cache_creation, context`). The objects are equal;
   the text differs in key order for these two types only. Route, text, thinking, tool_use, tool_result, step and
   done match Node's text byte for byte (tested).
2. **A scripted `route` with fields left out** (the Node tests' partial ones) reads as a route, and writes the
   missing fields back instead of leaving them out: `""` for `provider`, `label` and `providerLabel`, `null` for
   `engine`, `model`, `effort` and `vendor`, `false` for `streaming` and `backup` (pinned by a test since fix round
   1; this line used to say `null`/`false` for all). The turn layer's own routes always have all nine. A scripted
   `usage` with counts left out no longer gains them (fix round 1).
3. **An event one of whose known fields has the wrong shape** (`{type:"done", stopReason: 7}`) is `TurnEvent::Other`,
   so nothing is lost, but it is no longer a done to whoever matches on the variant. Only a scripted engine can
   produce one.
4. **Token counts are whole numbers.** A fractional, negative or `null` count makes the event `Other`.
5. **`{type: 3}`**: a numeric `type` is no type (kept as `Other`).

## Looks like a bug in the Node code

Ported as they are (as shapes); for the packages that port the behaviour:

1. **An error yielded after output gains its `code` later** (`ai/turn.js` `runAttempt`: `res.failure.code = ...` runs
   after the same object was already yielded). A consumer that serialised it when it arrived saw no `code`; one that
   kept the object sees `code: null` once the turn ends. Checked by running it (`{"type":"error","message":"plain
   failure"}` as yielded, `..."code":null}` afterwards). Rust events are values, so G3 has to pick; what a streaming
   consumer saw is "no code".
2. **`lib/tools.js` `checkToolPolicy` reads `ctx.channel`, which no caller ever sets**, so Tool Permissions'
   per-channel rules never apply and the audit log's actor is always "agent". `ToolContext::channel` is there, unset.
3. **`routes/chat.js` and `channels/websocket.js` read `event.name` on a `tool_result`**; no engine sets one (the web
   chat falls back to the tool's name from its own timeline; the WebSocket sends none).
4. **`ai/verify-model.js` puts `verify: true` in the tool context and passes `store` to `runTurn`**; nothing reads
   either. `ToolContext::verify` is there; `store` is not modelled.
5. **`extractPlaybookPrompt` gives `""` for a response that is the prefix alone**, which the callers' `if (playbook)`
   takes for "no playbook", so they would send the bare `__PLAYBOOK__` line to the person.

## What does not fit the interfaces cleanly

- **Per-call managers and stores.** Node tests handed a different fake `channelManager` or `settingsStore` to each
  `executeTool` or `runTurn` call. For a tool and a turn they are the app's here, so such a test makes one app per
  case (or re-scripts the fake). (A command, the system prompt and the diagnostics still take the manager from
  their caller: fix round 1.)
- **`lib/commands.js` reads `ctx.clearConversation`, `ctx.abortController` and `ctx.ai`.** No caller in `src/`
  passes them (two are dead hooks, one is a test seam), so they are not in `CommandContext`; K1 keeps them inside
  `lib/commands.rs`. (`autoSummarize`, which this line used to name, is passed by `test/commands-model.test.js` and
  read by nothing: fix round 1.)
- **The engines' `opts.deps`** (their tests' seams) and `opts.provider` (a fallback for a missing target) are not in
  `EngineOptions`: each engine defines its own seams.
- **The channels' constructor seams** (`apiRoot`, `Client`, `slackApiUrl`, `connectTimeoutMs`, `slackFilesOrigin`,
  `healthTimeoutMs`, `ImapFlow`, `smtpTransport`) are each channel's own. `chatStream` is gone: install a
  `FakeTurnRunner`.
- **Laziness.** A JS generator runs nothing until first read, and its `finally` runs on `return()`. The fakes keep
  both (a call is recorded at the first read; a dropped stream stops). The real turn layer and engines must stop
  their work when their stream is dropped; that is written on `TurnStream` and `Engine`, and is theirs to do.
- **`ChannelApi::stop` and `start_all` return `Result`** although the Node ones never reject: their callers have
  `catch` branches (`routes/admin.js` answers 400), which a failing fake lets a test reach.
- **Background-work tests before G3.** `test/background-callers.test.js` and `test/scheduled-tasks.test.js` script an
  engine under the real turn layer. S5 runs before G3, so it can only port them against `FakeTurnRunner`
  (INTERFACES.md says how); the assertions about what the turn layer resolved wait for G3.

## Risks

What a reviewer should look at first:

1. **`TurnEvent`'s hand-written reading** (`from_value`, `without_type`) and the flattened `extra` maps: this is what
   keeps unknown fields and unknown events. The derive could not do it (serde reads a numeric tag as a variant index,
   and a flattened `Option` of all-optional fields always reads as `Some`).
2. **What was left out of the contexts** (`db`, `settingsStore`, `auditLog`, `convStore`, a tool's
   `channelManager`, the commands' three extras). If a package turns out to need one per call rather than per app,
   the struct grows a field. (It did once: the command context's channel manager, fix round 1.)
3. **`TurnStream` items being `Result`.** Every consumer has to say what an `Err` is to it. The alternative (errors
   only as events) could not express the Node `catch` paths.
4. **The `Channel` trait's defaults for what a bot lacks**, and `ChannelHealth` as an enum of the two shapes that
   exist.
5. **The `install(app)` convention**: nothing enforces it until Z1's boot test.

## Fix round 1

The review (`reports/I0-review.md`) had one Important and four Minor findings. All five are addressed. One part of
finding 3 (a partial scripted `route`) is answered by correcting the documents and pinning the behaviour; there the
code stands, and the reason is below.

### 1. A command could not tell whether its caller handed it the channel manager (Important): fixed

- `CommandContext` has a fourth field, `channel_manager: Option<Arc<dyn ChannelApi>>`: the Node `ctx.channelManager`
  itself, not a flag. A caller sets it exactly where the Node caller did (`routes/chat.js` `POST /send`:
  `channel_manager: channel_manager(app)`); the five channels and the WebSocket leave it `None`
  (`..Default::default()`). K1 ports `if (ctx.channelManager)` as `if let Some(manager) = &ctx.channel_manager` and
  hands `ctx.channel_manager.clone()` on to `run_diagnostics`.
- I chose the manager over a flag because a line-by-line port is then right on both sides without knowing a rule,
  including the case Node had for free: the web chat before the app has a manager (`req.app.get("channelManager")`
  undefined) shows no channels line.
- The struct can no longer derive everything: `Debug` shows whether a manager is there, `PartialEq`/`Eq` compare the
  three plain fields and the manager by identity, and the serde derives are gone (nothing serialised a context).
  `CommandContext::with_channel_manager` is the Node `{ ...ctx, channelManager }`.
- `INTERFACES.md` rule 1 is rewritten (see finding 2), the comments in `command_api.rs` and `tool_api.rs` say which
  context has what, and the comment on `channels::api::channel_manager` says who may call it.
- Tests:
  - `lib::command_api::tests::a_command_has_the_channel_manager_only_when_its_caller_handed_it_over`: a handler that
    answers `/status` as `lib/commands.js` does, with the app's manager installed throughout. No channels line from
    a channel's context; `📡 **Channels:** telegram: running · slack: error` from the web chat's (the line Node

### 3. `Usage::merge_into` made up zero counts; a partial route's written-back fields (Minor): usage fixed, route documented

- **Usage: fixed.** The four counts (and `context_input_tokens`) are `Option<u64>`: `None` when the object had none,
  left out again when written. `Usage::new` sets all four, as the engines do; `Usage::default()` is `{}`. A count that
  is `null` or not a whole number does not fit, so its event is kept whole as `Other` rather than losing the field.
  `input()`, `output()`, `cache_read()` and `cache_creation()` are the Node `|| 0`; the field itself is the Node
  `?? null`. `merge_into(&mut Map)` is replaced by the typed `Usage::merge(&mut self, later)`, which is
  `{ ...usage, ...event.usage }` (nothing had used `merge_into` yet; `INTERFACES.md` shows the new one).
- Tests:

- **A partial `route`: the code stands.** `provider`, `label` and `providerLabel` stay `String`; `streaming` and
